# ADR-020 — Проверяемая материализация и доказательство покрытия

Статус: proposed, P0-4/P0-5, обновлено 2026-11-17.

## Источник и полнота

- Источник — только личное чтение активного студента с проверенной группой, неделей и подтверждённой **полнотой**: `identity_verified=True`, `source_complete=True`.
- `source_digest` — версия полного исходного снимка; ссылки могут обогащаться отдельно, не меняя версию расписания.
- Старые записи до 0065 по умолчанию имеют `source_complete=False`. Они не служат доказательством обхода; автоматического backfill подтверждений нет.
- Частичная, сомнительная, неподтверждённая загрузка никогда не удаляет чужие факты. Подтверждённая пустая полная неделя может убрать старые строки данного источника, но не доказывает `covered`.

## Замена и происхождение

- Каждая разделяемая строка содержит `source_user_id`, `source_week_start`, `source_snapshot_id`, `source_scope` (`common`/`subgroup`), `source_checked_at`, `materialized_at` и, при необходимости, `source_split_id`/`source_subgroup_id`.
- Новая полная версия удаляет старые общие и подгрупповые строки **этого источника и недели**, затем добавляет актуальные. Изменение преподавателя, аудитории или времени не оставляет прежнюю пару.
- Личные строки и прямые ссылки студента имеют приоритет. Совпавшая независимо полученная строка другого источника не переписывается. Ранее материализованные чужие строки никогда не становятся собственным источником.
- Подгруппа передаётся только при совпадении двух подтверждённых выборов. Изменения подгруппы после source-check не переопределяют старые факты. API повторно фильтрует материализованные строки по текущей подгруппе.
- Legacy строки без достоверного provenance не используются в новом чтении как проверенные.
- Источник, все активные получатели и `RanepaMaterializationReceipt` обновляются **в одной транзакции**. Сбой любого получателя отменяет всю операцию. В worker основной source-save объединён с материализацией; обогащение Moodle/SDO ссылками остаётся отдельной необязательной транзакцией.

## Доказательство covered

- `RanepaMaterializationReceipt` — атомарная запись `(group_id, recipient_user_id, week_start, source_user_id)` с `source_digest`, временем проверки и JSON-областями common/subgroups.
- `covered` разрешён только при наличии собственного получательского снимка и подтверждения доставки для **той же группы, получателя, недели и текущих подгрупп**.
- Источник должен по-прежнему состоять в группе, быть полным, подтверждённым и свежим (до шести часов), а его digest и checked_at должны совпадать с receipt. Прежнее receipt после смены версии источника недействительно.
- Пустые и непроверенные снимки не дают receipts. Общая часть без необходимой подгруппы не доказывает покрытие этой подгруппы; неизвестный выбор подгруппы не позволяет исключить аккаунт.
- `covered` — только пропуск избыточного обхода, не успешный фактический вход в СДО. Ошибка обязательной материализации переводит обход в failure и оставляет совместимый backup в очереди.
- Шестичасовая периодичность — политика планирования, а не доказанный SLA.

## Совместимость, миграция и откат

1. Миграция 0065 после 0064 добавляет два обратносуместимых внутренних поля и таблицу receipts. Публичный OpenAPI/TypeScript контракт не меняется.
2. Старые source snapshots и coverage сознательно не backfill-ятся: для разрешения `covered` нужны новые полные проверенные обращения и успешная запись.
3. Перед rollout требуется обязательный тест на Postgres с upgrade 0053 → 0065 и rollback на тестовом окружении, а затем отдельное разрешение владельца и canary.
4. Откат приложения до pre-0065 при уже применённой миграции допустим только при контролируемом плане совместимости; downgrade 0065 удаляет receipts/provenance proof и требует возобновить реальные проверки, иначе нельзя заявлять covered.
5. Не выполнять `merge`, production migration и deploy без отдельного разрешения.

## Контрольные тесты

- Исчезновение одной из двух пар, изменение преподавателя/времени/аудитории, повторный запуск без дубля.
- Пустой полный и пустой частичный источники, сохранение личной пары и прямой ссылки.
- Изоляция подгрупп, смена подгруппы, устаревший источник, выключенный участник, несколько групп.
- Ошибка второго получателя → rollback без receipts, неуспешная материализация → не `covered`.
- Все checks CI обязательны, но green CI не является доказательством production SLA или качества поиска ссылок.
