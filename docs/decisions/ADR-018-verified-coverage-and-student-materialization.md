# ADR-018 — Coverage-aware очередь и безопасная материализация фактов

Статус: proposed, P0-4/P0-5, 2026-11-16.

## Модель

Получение фактов (проверенный личный account crawl) и отображаемая
материализация (проверенная общая часть другим студентам) — разные этапы.

* Только `RanepaPersonalSnapshot.identity_verified=True` и активное
  членство могут быть источником для распространения.
* Разделённый по `SubjectSplit` предмет распространяется только при
  совпадении подтверждённых `MemberSubgroup` представителя и получателя.
  Нет ответа о подгруппе — нет распространения предмета.
* Общие предметы без признаков подгруппы можно использовать для всех
  активных участников одной группы. Неопределённые признаки подгруппы
  не трактуются как общий поток.
* `source_scope`, `source_checked_at`, `materialized_at` и
  `source_split_id`/`source_subgroup_id` находятся в JSON строки,
  без изменения обязательного wire-контракта.
* Личные поля и прямые ссылки имеют приоритет. `course_url` сохраняется
  отдельным от verified `online_url` полем. Ошибка одной записи требует
  rollback всей транзакции материализации, не откатывая уже сохранённый
  проверенный снимок источника.
* Чтение API перепроверяет текущую подгруппу даже для ранее
  материализованной строки. Изменение подгруппы не раскрывает старую строку.
* При обычном обходе `claim_next` может пометить избыточный job как
  `covered`, только если есть свежие identity-verified снимки других
  активных участников, закрывающие нужные подтверждённые подгруппы.
  Нет свежего покрытия или был failure — следующий аккаунт остаётся в очереди.
  Явный адресный pilot и owner-approved rescan обходят suppression.

## Совместимость и ограничения

Без миграции, без передачи credentials/cookie между студентами,
без изменения обязательных полей `/v1/ranepa-schedule`.
Состояние очереди `covered` означает экономию обхода, **не**
завершённый source crawl. Существующая 24-часовая политика повторных
попыток пока сохранена; SLA 6 часов требует отдельного решения владельца.
Сложные динамические предметные coverage matrix и второй контрольный
аккаунт для спорных фактов остаются следующими задачами, никакой
production rollout без canary и подтверждения владельца.

## Тесты/приёмка

- [ ] Одна общая пара доступна каждому применимому студенту.
- [ ] Подгруппа A не получает строки B, и наоборот.
- [ ] Повторный upsert не создаёт дубликаты, обновляет provenance.
- [ ] Сбой позднего получателя откатывает весь fan-out.
- [ ] Личная синхронизация не удаляет уже материализованные строки.
- [ ] Переключение подтверждённой подгруппы фильтрует старые строки.
- [ ] Свежий представитель экономит обход дубля, неподтверждённая
  подгруппа сохраняет требование дополнительного обхода.
- [ ] CI проходит до готовности к merge.

## Решения владельца перед rollout

Утвердить SLA и необходимость второго независимого контрольного
аккаунта перед первым распространением в новую группу.
