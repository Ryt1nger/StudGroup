# ЛК/СДО РАНХиГС: технический аудит и план пилота

**Состояние на 11.11.2026.** Это единый актуальный отчёт по готовности модуля. Автоматический обход и показ личных снимков остаются выключенными.

## Итог

Модуль технически близок к контролируемому пилоту, но ещё не подтверждён реальным сквозным запуском штатного worker. Код хранения реквизитов, очереди, браузерного чтения, проверки расписания и сохранения снимков существует и покрыт локальными тестами. YDB ранее прошла реальный одноразовый CRUD. Production backend на commit `4f0c5ba2d3c4a32fc2673b36866b5850753f284b` развёрнут на Render, deployment `dep-dbq9dljbc2fs739c4th0` имеет статус `live`; `/ready` и `/health` вернули HTTP 200.

В ходе этого аудита подготовлены commit `c482ddc` и PR №125: они ограничивают соединения штатного worker, добавляют десятиминутный предел одного аккаунта и исключают повторную загрузку уже открытой страницы расписания перед каждой неделей. Плановый workflow не включался, реальные реквизиты не использовались, production-данные не изменялись.

## A. Проверенное состояние

### Работает и подтверждено кодом или тестами

- Формы регистрации и профиля используют единый серверный путь реквизитов ЛК/СДО.
- Согласие на СДО проверяется перед постановкой в очередь и повторно перед получением реквизитов.
- В Supabase хранится только непрозрачный `sdu_credential_id`; логин и зашифрованный пароль находятся в отдельной YDB.
- Отзыв согласия удаляет запись YDB и не сообщает успех без подтверждённого удаления.
- Очередь содержит только идентификаторы, состояние и безопасный код ошибки.
- Очередь чередует группы и сначала выбирает пользователей, покрывающих новые подтверждённые подгруппы.
- Повтор одного завершённого аккаунта допускается не раньше 24 часов.
- `concurrency` GitHub Actions запрещает второй параллельный RANEPA worker.
- Worker открывает один браузер на аккаунт, использует одну браузерную сессию и повторно входит при истечении сессии.
- Месячная сетка сверяется с шестью пересекающими месяц неделями. Неполная, пустая без подтверждения или противоречивая неделя не сохраняется.
- СДО открывается только для занятий с соответствующей отметкой. Курс, прямая встреча, отсутствие ссылки, неоднозначность и ошибка доступа имеют разные состояния.
- Каждая полностью проверенная неделя сохраняется отдельно. Ошибка следующей недели не удаляет последний успешный снимок.
- Названия предметов нормализуются только для явных дублей; похожие названия не объединяются догадкой.
- Пароль не включается в очередь, API и штатные сообщения об ошибках.

Проверки текущего изменения:

- `ruff check` и `ruff format --check` — успешно;
- 125 профильных тестов РАНХиГС, согласий, профиля, ссылок и конфигурации — успешно;
- полный backend-набор: 1549 успешно, 37 пропущено, 2 старых сбоя вне модуля ЛК/СДО;
- последние production CI для commit `95cce474267f98b9eb70dcb0e8db03bf16643e03` и YDB smoke workflow — успешно;
- Backend CI PR №125 дошёл до уже воспроизведённого старого сбоя AI/дедлайнов и остановился по `--maxfail=1`; профильный набор ЛК/СДО остаётся зелёным;
- последние плановые RANEPA workflow — `skipped`, что подтверждает выключенный флаг.

### Подтверждено только прежней ручной проверкой

- На единственном тестовом аккаунте БИ 1.2 ранее считано 71 занятие ноября 2026 года; месяц совпал с недельными карточками.
- Для 16 карточек СДО были открыты страницы курсов; одна прямая ссылка на встречу была выбрана однозначно.
- Прямой HTTP GET авторизованной страницы вернул HTML без сетки расписания. Для текущего интерфейса нужен браузерный путь.

Это подтверждает парсер и маршрут одного аккаунта, но не работу production-worker, другую подгруппу или другие группы.

### Частично работает или требует production E2E

- Реальное сохранение реквизитов из Mini App в YDB и последующее чтение именно штатным worker ещё не пройдено одним сквозным сценарием.
- Повторный вход после реально истёкшей production-сессии проверен синтетически, но не отдельным production E2E.
- Telegram и Mini App ещё не проверены после результата штатного worker.
- Один аккаунт не подтверждает корректность другой подгруппы.
- Долговременное число соединений после нескольких deployment и запусков worker ещё не измерено.

### Не включено

- `RANEPA_CRAWL_PILOT_ENABLED=true` не установлен.
- Массовый и постоянный обход не запущен.
- `RANEPA_SCHEDULE_VIEW_ENABLED` не включён для личных снимков.
- CAPTCHA не обходится и фиксируется отдельным безопасным статусом.

## B. Обнаруженные проблемы

### 1. Worker мог повторно исчерпать Supavisor

**Критичность:** высокая перед включением расписания.

Web backend использовал заданные `pool size 1` и `overflow 0`, но `ranepa_worker.py` создавал отдельный SQLAlchemy engine с настройками по умолчанию. Один процесс мог держать 5 постоянных и до 10 дополнительных соединений — весь прежний лимит session mode.

Затронутые файлы: `main.py`, `ranepa_worker.py`, `test_app.py`, `test_ranepa_worker.py`.

### 2. Повторная загрузка одной страницы расписания

**Критичность:** средняя, влияет на нагрузку ЛК и время обхода.

После чтения месяца worker перед каждой из шести недель снова выполнял переход на тот же URL, хотя страница и авторизованная сессия уже были открыты.

Затронутые файлы: `ranepa_browser.py`, `test_ranepa_browser.py`.

### 3. Не было общего предела времени одного аккаунта

**Критичность:** средняя.

Отдельные переходы имеют тайм-ауты, но их сумма при медленном ЛК/СДО могла занять почти всю GitHub-смену. Это повышало риск жёсткого завершения процесса и лишних минут runner.

Затронутые файлы: `ranepa_worker.py`, `test_ranepa_worker.py`.

### 4. Избыточная подготовка очереди

**Критичность:** средняя для 150 пользователей, не блокирует одиночный пилот.

Каждая получасовая смена снова читает всех активных участников, а затем отдельно проверяет профиль, согласие, подгруппы и наличие задания. При 150 аккаунтах это создаёт сотни мелких SQL-запросов на запуск даже при неизменной очереди.

Без отдельного решения это не изменено: пропуск подготовки может задержать только что подключившегося пользователя, а выбор одного представителя вместо всех меняет утверждённое поведение личных снимков.

### 5. Повторные курсы СДО читаются по каждому занятию

**Критичность:** низкая для одного аккаунта, потенциально средняя на группе.

Если один курс встречается в нескольких неделях или у нескольких студентов одной подгруппы, его HTML открывается повторно. Без фактического измерения совпадающих переходов кэш не добавлен: ссылка может появиться ближе к занятию, а слишком долгий общий кэш приведёт к пропуску изменения.

### 6. Два старых сбоя полного backend-набора

**Критичность для ЛК/СДО:** отсутствует.

Падают тесты `test_inferred_and_attention_markers_are_hidden_from_students` и `test_students_see_the_neutral_label_and_then_the_confirmed_deadline`. Они относятся к AI/дедлайнам, воспроизводятся на актуальном `main` без текущих изменений и не затрагивают интеграцию РАНХиГС. Профильный набор полностью зелёный.

## C. Выполненные исправления

1. Для Supabase session pooler на порту 5432 добавлены безопасные значения по умолчанию: `pool_size=1`, `max_overflow=0`, `pool_timeout=10`. Явные настройки оператора сохраняют приоритет.
2. Оба режима worker используют общий конструктор engine, `pool_pre_ping`, скрытие SQL-параметров и те же ограниченные настройки.
3. Один аккаунт ограничен десятью минутами. По тайм-ауту сохраняются старые снимки, а задача завершается безопасным кодом `source_unavailable`.
4. Уже открытая и отрисованная страница «Моё расписание» переиспользуется между месяцем и неделями. При истёкшей сессии прежняя логика повторного входа сохраняется.
5. Добавлены регрессионные тесты пула, явного переопределения настроек, worker engine, тайм-аута и повторного использования страницы.

## D. Соединения Supabase

### Выбранное решение

Пока остаётся Supavisor session mode на порту 5432, но каждый процесс StudGroup ограничен одним клиентским соединением без overflow. Это минимальное изменение, совместимое с текущим SQLAlchemy-кодом и session-level поведением.

Transaction mode на 6543 не включён. Официально он не поддерживает prepared statements и требует `statement_cache_size=0` для asyncpg. SQLAlchemy asyncpg dialect при выполнении запросов сам вызывает `prepare()`, поэтому простая замена порта без отдельной совместимой конфигурации и реального прогона рискованна.

### Проверенные факты

- До очистки прежний session pool достигал 15 соединений и блокировал deployment.
- После ограничения пула и успешного deployment соединения освобождались до одного прикладного backend-соединения.
- После последующего rolling deployment наблюдались три прикладных Supavisor-соединения, включая одно `idle in transaction`; лимит не исчерпан, но это пока только точечный снимок.
- Жизненный цикл web engine и worker содержит `dispose()` в `finally`; worker после текущего исправления не может создать пул 5+10.

### Что ещё проверить

- число соединений через 30–60 минут после deployment;
- число соединений до, во время и после одного ограниченного worker;
- отсутствие `idle in transaction` после завершения запросов;
- повторный deployment без ручного завершения сессий.

## E. Готовность к одному реальному обходу БИ 1.2

Один ограниченный проход можно проводить только после слияния текущего исправления и ручного E2E реквизитов. Массовый обход пока запускать нельзя.

Точные технические блокеры:

1. Текущий commit ещё должен пройти CI и быть развёрнут.
2. Нужно проверить `согласие → запись YDB → повторное чтение → обновление → отзыв → подтверждённое удаление` через реальные экраны.
3. После повторного сохранения тестовых реквизитов нужно вручную запустить ровно одну bounded-смену, не включая cron.
4. Нужно сверить снимок Supabase и отображение Telegram/Mini App.
5. Нужно измерить соединения и продолжительность до и после прохода.

## Экономичность постоянных обходов

### 1. Запросы одного прохода аккаунта

Точное число сетевых запросов браузера зависит от внутренних XHR и статических ресурсов сайта и без production-трассировки не доказано. На уровне действий worker один месячный проход выполняет:

- один вход в ЛК при отсутствии действующей сессии;
- одно открытие месячного представления;
- до шести недельных представлений;
- чтение карточек занятий в интерфейсе;
- один переход СДО на каждое занятие с пометкой СДО;
- не более одного входа в Moodle в рамках общей браузерной сессии;
- одно согласованное чтение YDB для получения реквизитов;
- несколько коротких транзакций Supabase: claim, до шести проверенных недель и finish.

Для ранее измеренного месяца БИ 1.2 это было 71 занятие, 16 переходов СДО и примерно 106–132 секунды. После текущего исправления исключаются до шести лишних переходов на корневую страницу расписания.

### 2. Что повторяется напрасно

- подготовка всей очереди каждые 30 минут при неизменных участниках;
- повторное чтение одинакового курса для нескольких занятий;
- полный личный обход всех студентов с одинаковым подтверждённым набором подгрупп;
- обновление `checked_at` и каталога предметов при неизменном digest — это небольшая, но намеренная запись свежести.

### 3. Что можно безопасно переиспользовать

- браузерную сессию внутри одного аккаунта — уже реализовано;
- уже открытую страницу расписания — реализовано текущим исправлением;
- последний подтверждённый снимок при любой ошибке — уже реализовано;
- общий предмет только после совпадения у двух представителей разных подтверждённых наборов подгрупп — уже реализовано в guarded fallback;
- подгрупповое занятие только для пользователя с тем же подтверждённым выбором — уже реализовано;
- HTML курса только в пределах одного короткого обхода и только по точному идентификатору курса — возможная следующая оптимизация после измерения повторов.

Нельзя без проверки переиспользовать чужие прямые ссылки СДО, неизвестную подгруппу или старый курс на длительный срок.

### 4. Ожидаемая нагрузка

Текущая очередь запускает один браузер последовательно. При прежнем измерении около двух минут на аккаунт и паузе 20 секунд:

- 1 аккаунт: примерно 2–3 минуты;
- 150 аккаунтов: ориентировочно 5,5–6,5 часа чистого кругового времени;
- одновременно: один браузер и после исправления один клиент Supabase;
- повтор успешного аккаунта: не чаще одного раза в 24 часа.

Это экстраполяция одного аккаунта, а не гарантия production.

### 5. Ограничения расхода

- один workflow через `concurrency`;
- 24 минуты на смену и 29 минут hard timeout GitHub Actions;
- 10 минут на один аккаунт;
- один браузер, без параллелизма;
- пауза не менее 20 секунд;
- один Supabase client без overflow;
- один YDB read на аккаунт;
- повтор аккаунта не раньше 24 часов;
- СДО открывается только для помеченных занятий;
- worker и расписание по умолчанию выключены.

### 6. Необходимые следующие оптимизации

До 150 аккаунтов действительно нужна одна измеримая оптимизация: заменить N+1-подготовку очереди набором ограниченных SQL-запросов или хранить безопасный момент последней подготовки. Она не должна задерживать новых подключившихся более согласованного интервала.

Кэш курсов между аккаунтами и выбор только представителей подгрупп пока не внедряются. Сначала нужно измерить долю одинаковых курсов и получить продуктовое решение, можно ли не создавать личный снимок каждому добровольно подключившемуся пользователю.

## F. Следующий этап

1. Создать PR текущего исправления и дождаться зелёного Backend CI.
2. Развернуть commit при выключенных `RANEPA_CRAWL_PILOT_ENABLED` и `RANEPA_SCHEDULE_VIEW_ENABLED`.
3. Проверить соединения после deployment.
4. Пройти ручной E2E реквизитов и отзыв согласия на тестовом аккаунте.
5. Повторно сохранить реквизиты и вручную запустить одну bounded-смену только для БИ 1.2.
6. Сверить YDB, очередь, личные снимки, предметы, ссылки, Telegram и Mini App.
7. Если результаты корректны, отдельно согласовать включение расписания для одного пилотного аккаунта; массовый cron включать только после стабильного полного цикла.

## Откат

1. Не включать либо немедленно выключить `RANEPA_CRAWL_PILOT_ENABLED`.
2. Остановить ручной workflow; последний подтверждённый снимок не удалять.
3. Вернуть предыдущий live deployment backend.
4. Не удалять миграции, согласия и снимки при откате кода.
5. Реквизиты удалять только по отзыву пользователя или отдельному решению владельца.
6. Перед повторным запуском проверить `/ready`, `/health`, YDB CRUD и число соединений.
