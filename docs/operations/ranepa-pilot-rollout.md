# Пилот СДО/ЛК и расписания РАНХиГС

## Состояние допуска

PR 68, 96 и 98 должны пройти общий CI на одной ветке и миграции 0054–0058 поверх уже применённых 0052–0053 на отдельной PostgreSQL БД. Один аккаунт БИ 1.2 проверяет путь и сохранение собственного расписания, но не доказывает изоляцию двух разных подгрупп. До утверждения документов оператора и места первичного хранения персональных данных парольная форма, фоновый обход и показ личного расписания в рабочем приложении выключены. Тестовый запуск с личным аккаунтом владельца допустим только в изолированной среде с явным согласием владельца; секрет не помещается в Git, CI, отчёт или логи.

## Порядок выката

1. Зафиксировать текущие версии backend и frontend, сделать проверяемую резервную копию рабочей PostgreSQL БД и отдельно сохранить конфигурацию флагов. Проверить, что рабочая БД — утверждённый проект, а ключ `PROFILE_ENCRYPTION_KEY` имеет резервную копию в управляемом хранилище.
2. На отдельной PostgreSQL БД с миграциями 0052–0053 применить `uv run alembic upgrade head`, убедиться в единственной голове `0058`, проверить регистрацию нового студента и старосты, повторное открытие Mini App, три отдельных согласия, отказ и пропуск СДО, зашифрованное сохранение, отзыв с удалением и отсутствие пароля в API и логах. Проверить истечение сессии ЛК, ошибку входа, недоступность СДО, CAPTCHA и сохранение последнего верного снимка.
3. После правового допуска развернуть совместимые backend и frontend, применить миграции 0054–0058 к рабочей БД при выключенных `RANEPA_CRAWL_ENABLED` и `RANEPA_SCHEDULE_VIEW_ENABLED`. Проверить `/v1/legal/status`, `/v1/onboarding`, `/v1/profile` и штатные расписание/предметы на существующем участнике. Миграция отмечает старые активные членства завершёнными, не заставляя их проходить регистрацию снова.
4. На аккаунте владельца БИ 1.2 записать действующие отдельные согласия через приложение, сохранить реквизиты в зашифрованном виде и выполнить один ограниченный обход. Сверить код группы в ЛК, количество карточек месяца и недель, предметы, разделение подгрупп и ссылки СДО. Запись недели допустима только при совпадении с месячной сеткой. Проверить чтение снимка обратно через `/v1/ranepa-schedule` и отсутствие чужих занятий.
5. Включить `RANEPA_SCHEDULE_VIEW_ENABLED` только после сверки личного снимка; открыть расписание, сегодня, карточку пары и предметы в Mini App владельца. Затем включить ограниченный `RANEPA_CRAWL_ENABLED` и расписание GitHub Actions для участников, имеющих действующее согласие. Очередь чередует группы и сначала выбирает разные подтверждённые подгруппы. Один браузер работает последовательно с паузой; неполный результат не стирает успешную неделю.

## Проверка после запуска

- В первые сутки: статус каждого ограниченного прогона, время последнего успеха, коды ошибок без секретов, возраст личного снимка, совпадение группы и подгруппы, число извлечённых предметов и прямых ссылок; отсутствие пароля, cookies и HTML в логах и ответах API.
- После отзыва согласия: реквизиты очищены, новые задания для аккаунта не создаются, уже взятое задание повторно проверяет согласие до входа.
- Перед расширением на другие группы: второй аккаунт из иной подгруппы и проверка маршрутизации данных; один аккаунт владельца не заменяет эту проверку.

## Откат

Сначала выключить `RANEPA_CRAWL_ENABLED` и `RANEPA_SCHEDULE_VIEW_ENABLED`, остановить запущенную смену и проверить, что обычное расписание приложения снова используется. Вернуть сохранённые версии backend/frontend. Миграции 0054–0058 не откатывать автоматически: downgrade удалил бы согласия, снимки и ключи связи; при необходимости выполнить отдельный план восстановления из резервной копии. При подозрении на утечку отозвать реквизиты через API и заменить ключ шифрования по процедуре ротации. Проверить `/v1/schedule`, `/v1/today`, `/v1/subjects`, открытие Mini App и Telegram `/start` после отката.

## Что должен утвердить владелец

Полное наименование/ФИО и статус оператора, адрес, контакт по персональным данным, ответственный; окончательные редакции политики, условий и отдельных согласий; фактическое место первичного хранения, копий, логов и подрядчиков (включая Supabase US West); допустимость автоматического доступа к ЛК и СДО по правилам вуза. До этого рабочий сбор паролей студентов и автоматический обход не включать.
