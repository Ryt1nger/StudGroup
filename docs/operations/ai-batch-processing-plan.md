# План: 2 вызова AI на пакет сообщений вместо 2 на каждое (только анализ, код не менялся)

## 1. Где сейчас создаётся отдельный запуск

- `processing.context_for(db, raw, group, now)`: ±7 дней, до 125 сообщений в каждую сторону
  от **одного** целевого сообщения.
- `shadow_worker.enqueue_shadow`: на каждое целевое сообщение одна `ShadowEvaluationRun`
  с `target_message_ids=[raw.telegram_message_id]`, полным контекстом в `input_json`.
  Уникальны `job_id` и `(raw_message_id, source_revision, analysis_generation)`.
- `backfill.enqueue_window` вызывает то же в цикле по сообщениям окна; `process_shadow_next`
  берёт один запуск, `shadow.run_shadow` делает Pass 1 + Pass 2 (+ необязательный repair).
- Следствие: соседние сообщения платят за почти одинаковый контекст по 2 раза.
- `batching.plan_batches` (микро-пакеты ≤25 сообщений/12,5 КБ) существует для другого контура
  (`AnalysisBatch`) и в shadow-путь не подключён.

## 2. Как не анализировать пересекающиеся контексты повторно

Группировать цели в окна: целевые сообщения группы, отсортированные по дате, режутся на
пакеты по `max_targets` (стартово 8) и лимиту байт. Контекст пакета = объединение
контекстов целей (дедуп по `(telegram_message_id, revision)`), общий для всех. Один Pass 1 и один
Pass 2 на пакет; `target_message_ids` содержит все цели пакета. Цели, у которых контексты не
пересекаются (разрыв > 7 дней), попадают в разные пакеты.

## 3. Связь результатов с исходными сообщениями

Основа уже есть: каждое предложение/кандидат несёт `evidence` (id + revision), адаптер проверяет
их по запросу. Для пакета добавить: (а) `ShadowBatchRun` + таблица связей
`(batch_run_id, raw_message_id, source_revision, analysis_generation)` — целевые сообщения;
(б) карточка относится к цели, если её evidence содержит id цели; (в) цель без единой карточки и
кандидата помечается «проанализирована, пусто» — отличать пустой результат от потерянного.
Запросы на чтение (`effective_validation`, preview, wave_results) агрегируют по связям.

## 4. Дедупликация и идемпотентность

- Ключ пакета: sha256 от отсортированных `(raw_message_id, revision)` целей + `analysis_generation`
  + версия промптов. Повторное создание возвращает существующий пакет.
- Сохраняется per-message уникальность: нельзя поставить цель в новый пакет, если для её
  `(raw, revision, generation)` уже есть завершённый запуск (одиночный или пакетный).
- Дубли карточек между пакетами снимает существующий resolver (по идентичности/источникам);
  дубли событий — по `EventRecord.fingerprint`.
- Правка/удаление сообщения (новая ревизия) делает недействительными только пакеты с этой целью.

## 5. Сравнение стоимости и качества до/после

- Оффлайн-replay на замороженных `input_json` (`shadow_replay`, `replay`): те же цели прогоняются
  одиночным и пакетным способом на одном провайдере/модели.
- Стоимость: токены и USD из `metrics_json`/`prompt_tokens`/`completion_tokens`/`charged_usd`
  на цель; ожидание — до N-кратного снижения для Pass 1 и общей части Pass 2.
- Качество: `evaluation.py` (сопоставление сущностей с эталоном: найдено/пропущено/лишнее, тип,
  дата, аудитория) + доля пустых/отклонённых/спасённых кандидатов. Критерий приёмки:
  recall и точность типов не хуже одиночного режима, стоимость на цель ниже.
- Оплатой гейтится `SHADOW_PACKAGE_CAP_USD`; платные прогоны — только по решению владельца.

## 6. Риски для существующих shadow-запусков

- Уникальные ограничения `shadow_evaluation_runs` рассчитаны на одну цель на запуск —
  нужна новая сущность, а не переиспользование строки.
- Бюджет/резервирование (`SHADOW_RESERVATION_USD`) и ретеншн 30 дней считаются на запуск.
- `stored.effective_validation` и `wave_results` предполагают один запуск = одна цель.
- Лимит вывода `max_output_tokens=4000` против `MAX_PROPOSALS`/`MAX_CANDIDATES=40` на пакет:
  при росте числа целей ответ может обрезаться — размер пакета ограничить по токенам.
- Качество в длинном контексте может снижаться (внимание модели) — поэтому сравнение п.5 обязательно.
- Привязка промптов: повышение версии (`cplus-extraction-N`) инвалидирует ключ пакета.
- Repair ограничен одним вызовом на ответ — на пакете это станет одним на много целей; нужен
  лимит `repair` на пакет и сохранение per-item семантики.
- Порядок внедрения: флаг `shadow_batch_enabled` (off), только shadow, затем сравнение, затем
  решение владельца. Существующие одиночные запуски не трогаются.
