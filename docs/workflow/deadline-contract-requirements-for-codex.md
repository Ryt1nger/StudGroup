8. **Интеграционные тесты с Postgres** (список в разделе 7).

## 1. Что возвращает политика (нужно положить в данные карточки)
- `deadline_at`, `deadline_date_only` (уже есть).
- `deadline_basis`: `explicit | relative_resolved | schedule_inferred | unknown`. В БД и контракте C+ сейчас другие значения (`ambiguous_range` и др.); словарь нужно согласовать. Состояния `conflict` для даты текста против даты модели нет (решение Q3).
- `deadline_reason` (машинный код: `explicit_source_date_literal`, `relative_message_date`, `next_subject_lesson`, `subject_unknown`, `schedule_unavailable`, `cancelled_lesson_in_window`, `no_lesson_day_in_window`, `several_dates_in_text`, `not_inferable_for_kind`, `unresolved_explicit_deadline` и др.). Хранить, чтобы староста видел объяснение.
- `timezone_confirmed` (bool): false, если у группы нет часового пояса и взят Europe/Moscow.
- История: прежние значения срока с источником (message_id, reply_to_message_id) при каждом изменении; не затирать.

## 2. API / мини-приложение
- Студент: при `schedule_inferred` показывать нейтрально «К следующему занятию»; при `unknown` «Срок уточняется». Тексты: `student_label`.
- Староста: при `schedule_inferred` показывать «Дата не найдена в сообщении, она выведена по расписанию. Уточните срок.» и действие «Уточнить срок». Тексты: `staff_note`.
- Нужны поля в ответах `/deadlines`, `/homework` (старостские) для `deadline_basis`, `deadline_reason`; в студенческом ответе достаточно готовой подписи (`deadline_label`), без внутренних кодов.

### 2a. Контрольные точки и события (решение владельца 18.10)
- Срок КТ и событий никогда не ставится по расписанию. События обычно всегда приходят с датой.
- Если у КТ (и любого события) дата не найдена: карточка ПУБЛИКУЕТСЯ сразу, а староста сразу получает запрос «установить срок». Функция `headman_request(decision, kind)` возвращает `set_deadline`; для ДЗ с выводом по расписанию возвращает `confirm_inferred_deadline`; иначе пусто.
- Нужно от Codex: тип запроса старосте (элемент очереди старосты) с идентификатором карточки и кодом запроса; действие «установить срок» в кабинете и боте; до установки студенты видят «Срок уточняется». Политику уведомлений не менять.
- Допущение (проверить с владельцем): правило применено ко всем видам, кроме ДЗ (КТ, тест, оценивание, зачёт, экзамен), а не только к КТ.

## 3. Расписание
- Уже есть: `schedule_patterns.week` (first/second), `valid_from/valid_until`, `cancelled`, `groups.first_week_anchor`, `schedule_exceptions`. Миграция для чередования недель не нужна.
- Нужно: данные семестра до 2026-12-27 (обе недели, якорь 2026-10-05; первая неделя начинается в понедельник 5 октября), и список дней без пар (праздники, каникулы) от владельца. Для политики нужен вход `no_lesson_days` (набор дат) или таблица исключений на уровне группы: Codex выбирает место хранения.
- Контекст для политики строится как `ScheduleDeadlineContext(lessons, covered_from, covered_until, ready)`; в `processing.py` окно сейчас обрезается до today+14 дней.

### 3a. Обновление расписания через кабинет (решение владельца 18.10)
Расписание будет обновляться в кабинете и персонально, и через старосту. Политика получает только `ScheduleDeadlineContext` и `no_lesson_days`, источник ей безразличен.
- Один источник правды: политика читает те же `schedule_patterns` и `schedule_exceptions`, что и экран расписания.
- Групповое и личное расписание разделять. Для сроков группового ДЗ только расписание группы, подтверждённое старостой или заместителем. Личные правки студента групповые сроки не меняют.
- Метаданные каждой правки: кто, когда, роль, способ ввода, версия.
- **Пересчёт после правки (решение владельца 18.10: автоматически).** Когда староста меняет расписание, срок всех карточек со `schedule_inferred` перестраивается автоматически: `rebuild_inferred_deadlines(cards, now, timezone, schedule, no_lesson_days)`. Расписание передаётся уже развёрнутым с двухнедельным циклом (первая и вторая неделя от якоря; цикл — 2 недели с двумя разными расписаниями), поэтому правка шаблона одной недели двигает только карточки, чья следующая пара попадает на эту неделю. Не пересчитываются: карточки с заблокированным сроком, с подтверждённым/явным/относительным сроком, и те, чей срок уже прошёл (архив). Каждое изменение возвращает старый срок для истории. Если после правки надёжного срока нет (например, пара отменена), результат «неизвестно» и запрос старосте. Задним числом уведомления не создавать.
- `ready` вычисляется из состояния расписания группы: подтверждено старостой, покрывает период до конца семестра, якорь чередования недель задан. Без `first_week_anchor` `schedule_data` возвращает `week_state = needs_clarification`; политика трактует это как «расписание недоступно».
- Дни без пар тоже вводятся в кабинете и хранятся рядом с расписанием группы.
- API-контракт (создание, правка, подтверждение, импорт) нужен от Codex в OpenAPI.

## 4. Подключение в C+
- `output_adapter.py`: правило `SERIOUS_CONFLICT_REASON` («дата модели расходится с датой в тексте → на проверку») противоречит решению Q3 (дата текста всегда выигрывает). Нужна правка: вместо отправки на проверку подставлять дату из текста. Не менять без подтверждения владельца: вопрос ему задан.
- Правило приоритета дат внутри карточки (владелец, 18.10): более поздний источник карточки с датой главнее более раннего (правка по событию, которую ИИ отнёс к этой карточке). Реализовано в `decide_deadline`.
- Адаптер должен вызывать `decide_deadline` после проверки структуры: передать вид карточки (`semantic_kind`), предмет, расписание, часовой пояс группы; затем `headman_request`.
- Исходные сообщения брать с их собственными timestamp, не временем обработки. Задним числом уведомления не создавать (политику уведомлений не менять).

## 5. Переносы и блокировки
- Перенос: `detect_reschedule(...)` возвращает решение только для однозначных случаев (явная новая дата; «перенесли на следующую пару» с надёжным расписанием). Всё остальное в очередь проверки старосты. Обновлять существующую карточку (не создавать дубль), сохранять старый срок в истории.
- Блокировка полей (Q6): староста может зафиксировать `deadline`, `subject`, `kind`, `title`, `description`. Сейчас есть только `manual_lock` на всю карточку. Нужна схема хранения заблокированных полей и применение `apply_field_locks` в resolver; при попытке AI изменить заблокированное поле хранить расхождение для проверки. Это изменение схемы, нужна отдельная миграция по решению владельца.

## 6. Архивация
- Архивировать сразу по сроку карточки: точное время, либо конец календарного дня группы для date-only; `schedule_inferred` без защиты (решение владельца). Нужен тест на границе, что полуночный timestamp с флагом date-only не архивирует карточку в начале дня (функция `archive_instant` в политике готова; проверить фактический джоб архивации).

## 7. Тестирование
- Юнит-тесты политики и обновлений: 60 тестов в ветке (`test_analysis_deadline_policy.py`, `test_analysis_deadline_updates.py`, `test_analysis_subject_resolver.py`), включая двухнедельный цикл.
- Нужны интеграционные тесты с Postgres: повторная обработка даёт тот же срок; перенос обновляет ту же карточку; заблокированное поле не меняется; date-only архивируется в конце дня; КТ без даты публикуется и создаёт запрос старосте; правка расписания старостой пересчитывает `schedule_inferred` с учётом первой/второй недели; сообщения чужой группы не влияют на срок.
