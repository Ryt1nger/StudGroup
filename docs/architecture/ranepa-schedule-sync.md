# Интеграция расписания РАНХиГС

## Назначение

Главный источник расписания — личный кабинет / опубликованное расписание РАНХиГС.
У каждой группы StudGroup свой полный официальный код. Пилот: БИ 1.2, Э-ОБ-385-04-26-02.
Важное различие: текстовый код не является подтвержденным UUID внутренней системы.
Поле соответствия внутреннему идентификатору следует заполнять только из реального ответа источника.

## Этапы реализации

1. Определить способ чтения по коду группы: публичный источник -> JSON/API личного кабинета -> браузерная автоматизация при необходимости. Проверить, что возвращаются именно пары БИ 1.2.
2. Валидировать данные: даты, время, предмет, преподаватель, аудитория, тип занятия, подгруппа, отмена и охват периода. Не трактовать CAPTCHA, HTML-ошибку или пустую страницу как пустое расписание.
3. Отдельно сравнивать текущую и полученную неделю по устойчивому идентификатору занятия. Повторный импорт должен быть идемпотентен; параллельные подгруппы не должны сливаться.
4. Сопоставлять занятия с подгруппами по уникальному совпадению фамилии преподавателя или явно указанному номеру подгруппы. При конфликте — не угадывать.
5. При наличии университетского источника не публиковать изменение по скриншоту. Вместо этого запускать внеплановую сверку кабинета; скриншоты использовать только как резервный источник при недоступности университета.
6. Включить еженедельное обновление после успешного пилота. Хранить последнее успешное расписание, время проверки и статус ошибки; не стирать данные при сбое подключения.

## Автоматические и ручные проверки

- Разные группы не должны смешиваться ни в чтении, ни в записи.
- Одинаковая пара из разных источников не должна дублироваться.
- Два преподавателя/аудитории в один слот остаются отдельными занятиями, пока не подтверждена связь с подгруппами.
- Повторный успешный ответ не вызывает лишних правок и уведомлений.
- При неудаче upstream сохраняются прошлые пары, а фото идут в существующую ветку review.
- После восстановления upstream актуальный кабинет снова становится главным источником.
- Проверить минимум две реальные недели БИ 1.2 с фактическим расписанием и входящими скриншотами.

## Отложенные решения владельца

На этапе включения автоматической публикации обсудить:
1. Как разрешать конфликты с ручной правкой старосты.
2. Что показывать студенту при нераспознанной подгруппе.
3. Когда полностью заменить расписание БИ 1.2 и как поступить с уже созданными исключениями.

## Статус

Подготовительный этап: реализованы сравнение снимков, детекция подгрупп, правило приоритета источника, консервативный HTML-экстрактор и отдельное хранение конфигурации и недельных снимков (миграция 0050) с тестами. Все новые сущности изолированы от действующего расписания.
Реальный UUID группы и стабильная автоматическая выгрузка ещё не подтверждены. Автоматическое обновление календаря не включено; новые записи никуда не публикуются. Действующий учебный календарь не изменён.
## Безопасная проверка публичной страницы

Когда будет установлен достоверный внутренний UUID конкретной группы, можно запустить read-only проверку:

    cd apps/backend
    uv run python -m studgroup.ranepa_probe --group-code 'Э-ОБ-385-04-26-02' --group-uuid 'UUID-ИЗ-ПОДТВЕРЖДЁННОГО-ИСТОЧНИКА'

Команда проверяет соответствие группы и присутствие временных диапазонов занятий, обнаруживает CAPTCHA/отказы и выводит только метаданные. Она **пока не извлекает все пары** и ничего не записывает в календарь. Не использовать UUID других групп ради формального успеха пилота.

## Технический статус реализации

- `ranepa_schedule.py`: нормализация кода группы, детерминированные снимки, сравнение, осторожное сопоставление подгрупп и правило приоритета источников.
- `ranepa_probe.py`: безопасный read-only HTTP-пробник, обнаружение недоступного источника и CAPTCHA, CLI с UUID.
- `ranepa_public.py`: извлечение только однозначно распознанных уроков из открытой HTML-страницы; неполный результат ещё не может быть опубликован.
- `ranepa_storage.py`: изолированная таблица связи группы с официальным кодом/UUID и отдельное хранилище снимков; не редактирует `schedule_patterns`.
- Проверки включают дедупликацию, разграничение групп, подгруппы, недоступный источник, различение изменений и сохранение снимков без воздействия на live.

Следующий обязательный этап — подтвердить UUID БИ 1.2, получить исходный HTML/JSON с **реальными** занятиями и проверить полноту парсера. После этого отдельным PR включить правила резервного расписания, фоновую синхронизацию и управляемую публикацию. Не считать локальные тестовые данные доказательством работоспособности соединения с РАНХиГС.

## 5 ноября 2026: реальный тест доступа

- GitHub Actions запустил настоящий headless Chromium с публичным адресом `my.ranepa.ru/schedule/`.
- Результат `{"status": "captcha"}`. Поэтому ни UUID БИ 1.2, ни полные пары не подтверждены.
- Код группы `Э-ОБ-385-04-26-02` используется для точного поиска без подстановки соседних групп.
- Ветка поддерживает независимый разовый запуск через GitHub Actions `RANEPA one-shot source probe`, вручную (`workflow_dispatch`).
- Для отдельного сетевого теста можно передать `RANEPA_PROXY_URL` через **GitHub Actions Secrets**, например `http://user:password@host:3128`; секрет не записывать в репозиторий и логи. Без этого секрета проверка идёт напрямую. Доступ из определённого региона ещё **не гарантирует** отсутствие CAPTCHA.
- Поскольку режим `preview_only` и недельные снимки не публикуют данные в `schedule_patterns`, никакие ошибки внешнего источника не должны уничтожить локальное расписание.

После подтверждения источника провести пилот БИ 1.2, сравнить минимум две недели, отдельно разрешить конфликты со скриншотами и только затем разрешить еженедельную автопубликацию.


## Локальный пилот на Mac: вход через интерфейс

Для личного кабинета, который не отдаёт расписание без сессии, есть отдельный
read-only браузер `apps/backend/scripts/ranepa_mac_pilot.py`.
Он использует **собственный** профиль Chromium в
`~/Library/Application Support/StudGroup/RANEPA Browser`, не читает существующие
профили Chrome, не копирует cookies на сервер и никогда не пишет в рабочую БД.
Содержимое профиля следует считать секретным: не пересылать, не помещать в Git
или облачные вложения; рекомендуется включённый FileVault.

Один раз на Mac в checkout PR №68:

```bash
cd apps/backend
uv sync --frozen
uv run --with playwright python -m playwright install chromium
uv run --with playwright python scripts/ranepa_mac_pilot.py --setup
```

В появившемся браузере пользователь самостоятельно выполняет вход в РАНХиГС
и открывает своё расписание. Затем возвращается в Терминал и нажимает Enter.
Никаких логинов, паролей или cookie в чат и GitHub отправлять не требуется.

Повторная проверка без повторного входа (если сессия ещё действует):

```bash
uv run --with playwright python scripts/ranepa_mac_pilot.py --headed --group-code 'Э-ОБ-385-04-26-02'
```

Для проверки реальной разметки после входа можно сохранить HTML только локально:

```bash
uv run --with playwright python scripts/ranepa_mac_pilot.py --headed --mode public --capture-html "$HOME/Library/Application Support/StudGroup/ranepa-week.html"
uv run python scripts/ranepa_html_check.py --html-file "$HOME/Library/Application Support/StudGroup/ranepa-week.html" --week-start 2026-11-02
```

Файл создаётся с правами `0600` вне репозитория и не перезаписывается. Он может
содержать личные данные и сессионные сведения: не прикладывать к PR, чату,
тикетам или CI. После локальной проверки удалить файл вручную. Обе команды
выводят только статус и агрегаты, без HTML, cookie, имён и названий занятий.
Если группа не подтверждена на странице, файл не создаётся. Код `preview_only`
всё ещё означает неполный, не публикуемый результат.

Прямой HTTP проверяется отдельно, только с **проверенным** UUID группы:

```bash
uv run python scripts/ranepa_html_check.py --direct-http GROUP_UUID --week-start 2026-11-02
```

Этот запрос не использует браузерную сессию или cookie. Его успех не доказывает,
что авторизованный HTML можно получить обычным HTTP; для такого вывода нужно
сравнить ответ того же URL с доступом пользователя, не раскрывая секреты.

`--headed` показывает ход браузера и полезен для первой диагностики; без него
проверка идёт в фоне. Вывод — JSON с состоянием доступа, агрегатами DOM
или **только подтверждёнными** занятиями; `complete: false` до сверки с ЛК.

Критически: авторизация через браузер и чтение интерфейса — разные этапы.
Сам факт `session_ready_for_test` не доказывает, что полный календарь
распознан. Если группа не видна в интерфейсе, возвращается
`group_identity_unverified`. Если разметка не подходит парсеру —
`parser_unverified`. Нельзя публиковать неполный результат.

6 ноября 2026 вход через обычный браузер в ЛК и СДО удался: раздел «Моё
расписание» показал реальные занятия БИ 1.2, а страницы курсов — реальные
кандидаты на ссылки. Это ручная проверка интерфейса, **не успешный запуск
автоматического парсера**. Полный автоматический импорт и запись в StudGroup
не проверены и не включены. Следующий шаг — read-only автоматический обход
того же интерфейса и сверка его результата с видимым расписанием.

## Согласованный недельный обход студентов

### План реализации и проверки

1. Подготовить детерминированное чередование групп и раннее покрытие
   подтверждённых подгрупп. В очередь передавать только идентификаторы.
   Проверить справедливость, повторы и отсутствие смешения групп тестами.
2. Добавить долговечные задания обхода и изолированные по группе результаты
   отдельных студентов, с состояниями попыток, временем проверки и
   идемпотентным повтором. Проверить перезапуск и частичные ошибки на БД.
3. Реализовать read-only браузерный вход и месячный сбор «Моего расписания»
   для одного подключённого аккаунта. Сверить даты, пары и подгруппу с ЛК.
4. Для пар с пометкой «СДО» обойти соответствующие курсы, извлечь кандидатов
   на ссылки и применить правила точного/неоднозначного сопоставления.
   Проверить на реальных курсах Алпеева, Клишиной и Федотовой.
5. Подключить ограниченный background worker и еженедельное планирование,
   измерить время и память на малой выборке, затем увеличивать охват.
6. Реализовать выдачу резервного снимка ботом с датой проверки и строгой
   видимостью подгрупп. Включать production-обновление только после сверки
   нескольких реальных аккаунтов и отдельного решения владельца.

Текущий код PR №68 покрывает только подготовительные части первого этапа и
read-only хранение групповых недельных снимков. Наличие тестов не означает,
что браузерный обход или еженедельная очередь уже работают.

Цель — заранее заполнить резервное расписание и ссылки для каждой группы.
Подключение университетского доступа предусмотрено при первой регистрации
студента: пользователь вводит логин и пароль в защищённой форме StudGroup.
Учётные данные нельзя помещать в групповые записи, снимки расписания, логи,
аналитику или репозиторий. До реализации формы нужно отдельно проверить
способ шифрования при хранении, ограничение доступа worker, смену/отзыв
учётных данных и обработку неудачного входа. Сам ввод и хранение доступа
пока не реализованы.

В начале недели система ставит в очередь аккаунты всех студентов, которые
подключили доступ. Отдельный фоновый worker последовательно обрабатывает
задачи с измеренным ограничением параллельных браузеров; завершение всего
обхода за один час не требуется. Каждое успешное чтение сохраняется сразу,
а после перезапуска worker продолжает с незавершённых задач. Сбой одного
аккаунта не останавливает остальные.

Порядок очереди — справедливое чередование академических групп. В первых
кругах из каждой группы выбирать представителей **разных подтверждённых
подгрупп**, прежде чем брать второго студента той же подгруппы. Если вход
представителя не удался, другого студента этой подгруппы поставить в
ближайший круг. После первоначального покрытия обрабатывать остальных.
Неизвестная подгруппа остаётся неподтверждённой: частичный охват студентов
не доказывает полноту расписания всех подгрупп.

Каждая задача несёт неизменяемые идентификаторы студента и академической
группы. Перед сохранением сверять группу, увиденную в ЛК. Все записи,
снимки, подгруппы, ссылки и ошибки изолированы по академической группе;
личные сведения студента не становятся общегрупповыми автоматически.
Одинаковые подтверждённые пары из разных аккаунтов объединяются, различия
сохраняются для проверки. Подгрупповую пару выдавать только студенту с
подтверждённой принадлежностью к этой подгруппе. Не подменять её занятием
другой подгруппы.

Источник расписания — раздел **«Моё расписание»** ЛК, включая месячный вид.
Для каждого занятия сохранять дату, время, предмет, преподавателя, аудиторию,
тип, учебную группу/подгруппу и время успешной проверки. При сбое входа
показывать последнее подтверждённое расписание с отметкой актуальности,
не очищая его. CAPTCHA пока только фиксировать как недоступность аккаунта;
способ дальнейшего прохождения отложен.

Ссылки на дистанционные занятия искать **только** для карточек с пометкой
«СДО». После перехода к соответствующему курсу СДО читать всю страницу,
включая вложенные разделы. Кандидатов сопоставлять по предмету,
преподавателю, точному обозначению учебной группы, типу занятия, дате и
времени, если они указаны рядом со ссылкой. Тесты, задания, файлы и БРС
не считать входом на занятие. Постоянную ссылку без даты можно привязать,
если для преподавателя и группы она единственная; при нескольких подходящих
ссылках сохранять неоднозначность, а не выбирать произвольно. Вместе со
связью пары и ссылки хранить источник и время проверки. Сессионные параметры
ссылок перехода из ЛК не сохранять как общедоступный URL.

Ручная проверка 6 ноября дала примеры: в курсе истории у Алпеева указаны
точная учебная группа и даты 9, 16, 23 ноября; у Клишиной в курсе культуры
есть постоянная ссылка для соответствующей группы. У Федотовой в курсе
основ российской государственности найдено несколько ссылок для той же
группы без однозначной даты; соответствие 9 ноября не подтверждено. В
просмотренных курсах математического анализа и средств цифровой обработки
подтверждённая ссылка на онлайн-пару не найдена. Эти наблюдения — основа
для тестов сопоставления, но не доказательство полноты всех курсов.

Критерии приёмки перед включением записи: обойти реальные недели и месячный
вид нескольких студентов разных подгрупп; доказать изоляцию групп и точность
привязки ссылок; проверить частичный успех, повтор, перезапуск и выдачу
резервных данных при сбое. Production-синхронизация и замена действующего
расписания остаются выключенными до отдельного согласования.
