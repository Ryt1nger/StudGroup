# Интеграция расписания РАНХиГС

## Назначение

Главный источник расписания — личный кабинет / опубликованное расписание РАНХиГС.
У каждой группы StudGroup свой полный официальный код. Пилот: БИ 1.2, Э-ОБ-385-04-26-02.
Важное различие: текстовый код не является подтвержденным UUID внутренней системы.
Поле соответствия внутреннему идентификатору следует заполнять только из реального ответа источника.

## Этапы реализации

1. Определить способ чтения по коду группы: публичный источник -> JSON/API личного кабинета -> браузерная автоматизация при необходимости. Проверить, что возвращаются именно пары БИ 1.2.
2. Валидировать данные: даты, время, предмет, преподаватель, аудитория, тип занятия, подгруппа, отмена и охват периода. Не трактовать CAPTCHA, HTML-ошибку или пустую страницу как пустое расписание.
3. Отдельно сравнивать текущую и полученную неделю по устойчивому идентификатору занятия. Повторный импорт должен быть идемпотентен; параллельные подгруппы не должны сливаться.
4. Сопоставлять занятия с подгруппами по уникальному совпадению фамилии преподавателя или явно указанному номеру подгруппы. При конфликте — не угадывать.
5. При наличии университетского источника не публиковать изменение по скриншоту. Вместо этого запускать внеплановую сверку кабинета; скриншоты использовать только как резервный источник при недоступности университета.
6. Включить еженедельное обновление после успешного пилота. Хранить последнее успешное расписание, время проверки и статус ошибки; не стирать данные при сбое подключения.

## Автоматические и ручные проверки

- Разные группы не должны смешиваться ни в чтении, ни в записи.
- Одинаковая пара из разных источников не должна дублироваться.
- Два преподавателя/аудитории в один слот остаются отдельными занятиями, пока не подтверждена связь с подгруппами.
- Повторный успешный ответ не вызывает лишних правок и уведомлений.
- При неудаче upstream сохраняются прошлые пары, а фото идут в существующую ветку review.
- После восстановления upstream актуальный кабинет снова становится главным источником.
- Проверить минимум две реальные недели БИ 1.2 с фактическим расписанием и входящими скриншотами.

## Отложенные решения владельца

На этапе включения автоматической публикации обсудить:
1. Как разрешать конфликты с ручной правкой старосты.
2. Что показывать студенту при нераспознанной подгруппе.
3. Когда полностью заменить расписание БИ 1.2 и как поступить с уже созданными исключениями.

## Статус

Этап подготовки ядра: реализовано сравнение снимков, детекция подгрупп и правило приоритета источника с unit-тестами.
Реальный UUID группы и стабильная автоматическая выгрузка ещё не подтверждены. Действующий учебный календарь не изменён.
## Безопасная проверка публичной страницы

Когда будет установлен достоверный внутренний UUID конкретной группы, можно запустить read-only проверку:

    cd apps/backend
    uv run python -m studgroup.ranepa_probe --group-code 'Э-ОБ-385-04-26-02' --group-uuid 'UUID-ИЗ-ПОДТВЕРЖДЁННОГО-ИСТОЧНИКА'

Команда проверяет соответствие группы и присутствие временных диапазонов занятий, обнаруживает CAPTCHA/отказы и выводит только метаданные. Она **пока не извлекает все пары** и ничего не записывает в календарь. Не использовать UUID других групп ради формального успеха пилота.
