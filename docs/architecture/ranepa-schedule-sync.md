# Интеграция расписания РАНХиГС

## Путь данных

После вступления в группу с кодом РАНХиГС бот предлагает открыть форму подключения в профиле StudGroup. Студент вводит там логин и пароль. Сервер шифрует их ключом `PROFILE_ENCRYPTION_KEY`; API возвращает только состояние подключения. Отзыв доступа удаляет реквизиты. Фоновый worker получает из очереди только идентификаторы студента и группы, расшифровывает реквизиты в памяти и открывает раздел ЛК «Моё расписание». При истечении сессии он входит повторно. CAPTCHA фиксируется как ошибка; её прохождение не реализовано.

У каждой группы StudGroup свой официальный код. Перед записью worker читает активную роль в профиле ЛК и сверяет точный код. Он получает месячную сетку, затем каждую пересекающую месяц неделю, сверяя все карточки по дате, времени и названию. Неполный HTML, ошибка входа или неверная группа не заменяют последнюю успешную запись. Полностью пустая неделя принимается только после проверки месячной сетки.

Каждая проверенная неделя сохраняется в `ranepa_personal_snapshots` по `(group_id, user_id, week_start)` сразу после чтения. Расписание основного API `/v1/schedule` и ближайшая пара в `/v1/today` можно переключить на эти записи флагом `RANEPA_SCHEDULE_VIEW_ENABLED=true`. При включённом флаге и заданном коде группы старый общий календарь не подставляется вместо личного неполного результата: это защищает от показа занятий чужой подгруппы. API `/v1/ranepa-schedule` дополнительно сообщает полноту и время последней проверки. Флаг по умолчанию выключен.

Если аккаунт не прочитан, резерв берёт занятие только из той же группы и от студентов с подтверждённой учебной группой в ЛК. Для предмета с делением требуется одинаковый подтверждённый выбор подгруппы. Для общего предмета требуется совпадение занятия у двух студентов с разными подтверждёнными наборами подгрупп. Резерв всегда помечается неполным; чужая ссылка СДО не переносится.

Названия предметов из проверенных личных недель попадают в отдельный каталог группы и видны в «Предметах» и при определении предмета ДЗ/КТ. Пробелы и регистр нормализуются для явных дублей; похожие названия автоматически не объединяются.

Очередь чередует группы и сначала покрывает разные подтверждённые подгруппы. Один worker обрабатывает аккаунты последовательно с настраиваемой паузой. Он запускается отдельным контейнером `apps/backend/Dockerfile.ranepa-worker`; `RANEPA_CRAWL_ENABLED` по умолчанию выключен. Для рабочего запуска нужны отдельный сервис, общая БД, `PROFILE_ENCRYPTION_KEY`, браузер Chromium и контроль памяти и времени на небольшой выборке. В production сервис не создан.

Планирование 1000 аккаунтов не означает 1000 одновременных браузеров: при текущем ограничении это один браузер за раз. Локальный замер самого планировщика на 1000 синтетических идентификаторов из 50 групп: 0,063 секунды и 0,51 МиБ пиковой памяти; первые 50 заданий покрывают все 50 групп. Это **не замер браузерного обхода**. Один месячный обход включает вход, месячную сетку, до шести недель и страницы СДО. По одиночному локальному пилоту нельзя надёжно назвать время для 1000 аккаунтов; порядок величины при нескольких минутах на аккаунт — десятки часов, а не один час. До включения нужно измерить полный цикл на нескольких аккаунтах и настроить паузу и память worker по результатам.

## СДО

Worker следует из карточки ЛК в курс СДО только для пары с пометкой «СДО». Он читает HTML открытого курса и рассматривает URL-активности Moodle вида `/mod/url/view.php?id=...`. Ссылка привязывается к занятию лишь при точном обозначении потока/группы, фамилии преподавателя и дате занятия либо при единственной постоянной ссылке. Неоднозначность и отсутствие ссылки фиксируются, произвольный кандидат не выбирается. Сессионная ссылка перехода из ЛК не сохраняется.

Ручной просмотр 6 ноября 2026 выявил датированные ссылки у Алпеева и постоянную ссылку у Клишиной. Для Федотовой было несколько похожих вариантов. При автоматическом локальном прогоне двух недель соответствие СДО-ссылок не подтвердилось: проверено 6 карточек СДО, 0 ссылок принято. Поэтому связывание ссылок остаётся незавершённой проверкой и не должно включаться без дополнительных реальных образцов.

## Проверка и состояние

На авторизованном аккаунте БИ 1.2 с кодом `Э-ОБ-385-04-26-02` браузерный пилот прочитал 20 занятий за 2–8 ноября 2026 и 74 карточки месячной сетки ноября; 74 карточки совпали с недельными представлениями. Реальные 20 занятий были записаны и прочитаны обратно только во временной локальной SQLite БД. Это не импорт в рабочую базу StudGroup. Проверка неверного кода группы завершилась `identity_unverified`.

Локальный read-only прогон:

```bash
cd apps/backend
uv sync --frozen
uv run python -m playwright install chromium
uv run python scripts/ranepa_auth_readonly.py --group-code 'Э-ОБ-385-04-26-02' --week-start 2026-11-02 --month --local-db-check
```

Скрипт запрашивает логин и пароль без эха, не пишет HTML, cookies или секреты в репозиторий и выводит лишь агрегаты. `--sdo` добавляет проверку ссылок без публикации. Временная БД удаляется после теста. Снимки экрана и страницы авторизованной сессии не прикладывать к PR.

`--http-check` после браузерного входа делает отдельный GET той же страницы обычным HTTP-клиентом с сессионными cookies только в памяти. В результате выводятся лишь HTTP-статус и признаки отрисованной недельной/месячной сетки. Реальный запуск 6 ноября 2026 дал HTTP 200, но обеих сеток в HTML не было; тот же браузерный прогон прочитал 20 занятий. Значит, прямой GET страницы недостаточен. Возможность использовать отдельный внутренний API без браузера не проверена.

Перед production-включением нужно проверить несколько аккаунтов разных подгрупп, добиться подтверждённого сопоставления СДО на реальных курсах, измерить время и память ограниченного worker, проверить миграцию и полный CI. Затем требуется отдельное согласие владельца на включение `RANEPA_CRAWL_ENABLED` и `RANEPA_SCHEDULE_VIEW_ENABLED`, развёртывание сервиса и изменение рабочего расписания.
