# Интеграция расписания РАНХиГС

## Путь данных

После вступления в группу с кодом РАНХиГС бот предлагает добровольную форму СДО/ЛК `/profile/sdo` и отдельное согласие. Староста проходит тот же шаг после настройки группы. В `user_profiles` хранится только непрозрачный `sdu_credential_id`; логин и зашифрованный Fernet пароль находятся в отдельной YDB Serverless. Worker читает только действующее согласие и повторно проверяет его перед входом; отзыв подтверждённо удаляет запись YDB. Рабочего fallback пароля в Supabase нет. Фоновый worker получает из очереди только идентификаторы студента и группы, расшифровывает реквизиты в памяти и открывает раздел ЛК «Моё расписание». При истечении сессии он входит повторно. CAPTCHA фиксируется как ошибка; её прохождение не реализовано.

У каждой группы StudGroup свой официальный код. Перед записью worker читает активную роль в профиле ЛК и сверяет точный код. Он получает месячную сетку, затем каждую пересекающую месяц неделю, сверяя все карточки по дате, времени и названию. Неполный HTML, ошибка входа или неверная группа не заменяют последнюю успешную запись. Полностью пустая неделя принимается только после проверки месячной сетки.

Каждая проверенная неделя сохраняется в `ranepa_personal_snapshots` по `(group_id, user_id, week_start)` сразу после чтения. Расписание основного API `/v1/schedule` и ближайшая пара в `/v1/today` можно переключить на эти записи флагом `RANEPA_SCHEDULE_VIEW_ENABLED=true`. При включённом флаге и заданном коде группы старый общий календарь не подставляется вместо личного неполного результата: это защищает от показа занятий чужой подгруппы. API `/v1/ranepa-schedule` дополнительно сообщает полноту и время последней проверки. Флаг по умолчанию выключен.

Если аккаунт не прочитан, резерв берёт занятие только из той же группы и от студентов с подтверждённой учебной группой в ЛК. Для предмета с делением требуется одинаковый подтверждённый выбор подгруппы. Для общего предмета требуется совпадение занятия у двух студентов с разными подтверждёнными наборами подгрупп. Резерв всегда помечается неполным; чужая ссылка СДО не переносится.

Названия предметов из проверенных личных недель попадают в отдельный каталог группы и видны в «Предметах» и при определении предмета ДЗ/КТ. Пробелы и регистр нормализуются для явных дублей; похожие названия автоматически не объединяются.

Очередь чередует группы и сначала покрывает разные подтверждённые подгруппы. Один worker обрабатывает аккаунты последовательно с настраиваемой паузой. Через 24 часа после завершения аккаунт снова попадает в очередь, но ранее не обработанные аккаунты имеют приоритет. Один аккаунт ограничен десятью минутами. Для Supabase session pooler worker использует один клиент без overflow; при остановке engine освобождается через `dispose()`. `RANEPA_CRAWL_ENABLED` и отдельный допуск `RANEPA_ACCESS_APPROVED` по умолчанию выключены.

Бесплатный вариант запуска — `.github/workflows/ranepa-crawl.yml`: стандартный GitHub runner публичного репозитория запускается каждые 30 минут, обрабатывает очередь до 24 минут и завершает смену. Параллельные смены ограничены одной. По расписанию GitHub запускает workflow только из `main`; до слияния PR автоматического обхода нет. Для работы нужны репозиторные секреты `RANEPA_DATABASE_URL` (действующая PostgreSQL БД API, со схемой `postgresql+asyncpg://`), `RANEPA_PROFILE_ENCRYPTION_KEY` (тот же Fernet ключ, что у API), а также те же одобренные `LEGAL_OPERATOR_NAME`, `LEGAL_OPERATOR_ADDRESS`, `LEGAL_OPERATOR_CONTACT`, `LEGAL_DATA_REGION`, `LEGAL_DOCUMENTS_APPROVED`, что у API, и отдельный подтверждённый `RANEPA_ACCESS_APPROVED=true` после проверки правил вуза. Значения никогда не помещаются в YAML или вывод. Ветка PR не получает эти секреты через автоматические PR проверки. Владелец должен проверить доступ из GitHub runner к БД и провести ограниченный реальный запуск перед включением рабочего расписания. Запуски GitHub могут запаздывать или пропускаться, а браузерные страницы могут меняться; ссылки, появившиеся за минуты до пары, не имеют гарантированного времени обнаружения. Ранее подготовленный платный Render worker отменён и не применялся.

Планирование 1000 аккаунтов не означает 1000 одновременных браузеров: при текущем ограничении это один браузер за раз. Локальный замер самого планировщика на 1000 синтетических идентификаторов из 50 групп: 0,063 секунды и 0,51 МиБ пиковой памяти; первые 50 заданий покрывают все 50 групп. Это **не замер браузерного обхода**. Один месячный обход включает вход, месячную сетку, до шести недель и страницы СДО. Полный месячный локальный прогон одного аккаунта с 16 карточками СДО занял 111 секунд. Простая экстраполяция для начальных 150 аккаунтов и паузы 20 секунд даёт около 5,5 часов на один круг. Это не гарантия для GitHub: время зависит от числа курсов, доступности сайта и задержек расписания. До включения нужно измерить полный цикл на нескольких аккаунтах.

## СДО

Worker следует из карточки ЛК в курс СДО только для пары с пометкой «СДО». При переходе на форму входа Moodle он однократно входит с подключёнными реквизитами. Он читает HTML открытого курса и рассматривает активности Moodle `/mod/url/view.php?id=...` и `/mod/mtslinkrnhgs/view.php?id=...`. Ссылка на встречу привязывается к занятию лишь при точном обозначении потока/группы, фамилии преподавателя и дате занятия либо при единственной постоянной ссылке. Если в названии есть время начала, оно также должно совпасть; поддерживаются даты с двух- и четырёхзначным годом. Неоднозначность, совпадение преподавателя/потока без подтверждённого времени (`timing_unverified`) и отсутствие ссылки фиксируются отдельно; произвольный кандидат не выбирается. Решение по ссылке сохраняется в личном снимке как `link_state`; отсутствие активностей встречи в проверенном курсе отличается от ошибки доступа. Подтверждённый адрес курса сохраняется отдельно как `course_url` и показывается в карточке пары как запасной переход в СДО, не как ссылка на конкретную встречу. Сессионная ссылка перехода из ЛК и дополнительные параметры Moodle URL не сохраняются.

Ручной просмотр 6 ноября 2026 выявил датированные ссылки у Алпеева и постоянную ссылку у Клишиной. Для Федотовой было несколько похожих вариантов. Повторный месячный прогон 8 ноября проверил 16 карточек СДО в пересекающих месяц неделях: все 16 переходов привели к подтверждённому курсу; 1 ссылка на встречу выбрана однозначно, 10 курсов не содержали активностей встречи, для 5 карточек в курсе не нашлось единственного подходящего варианта. Диагностика реального HTML обнаружила активности «МТС Линк», которые прежний парсер пропускал; их поддержка добавлена, но при этом месячном прогоне новых однозначных ссылок не появилось. У Федотовой есть несколько активностей с одинаковыми преподавателем и потоком, у Алпеева в открытом курсе нет активности с его фамилией. Повтор недели 9–15 ноября после разделения статусов дал 4/4 подтверждённых курса, 0 прямых встреч: два `no_course_links`, один `not_found`, один `timing_unverified`. Подтверждена пара «Культура личности и общества» 16 ноября 2026 и чистый Moodle URL `https://lms.ranepa.ru/mod/url/view.php?id=1425553`: совпали фамилия Клишиной и точное обозначение потока, ссылка в курсе единственная постоянная. Остальные ссылки не выдумываются; пользователь может открыть соответствующий курс и найти сведения там. Месячная сетка 8 ноября совпала с недельными: 71/71 карточка; прогон занял 105,7 секунды. Связывание прямых ссылок остаётся частичным и требует проверки на других аккаунтах и курсах.

## Проверка и состояние

9 ноября 2026 объединённая ветка PR 99 прошла read-only месячный прогон на единственном доступном аккаунте БИ 1.2: 71 карточка месячной сетки совпала с 71 карточкой недель; 16 переходов СДО открыли подтверждённые страницы курсов, одна прямая ссылка на встречу была однозначной. Для остальных: 10 `no_course_links`, 4 `not_found`, 1 `timing_unverified`. Прогон занял 132,4 секунды. Прямой HTTP вернул 200 без сеток недели и месяца. Промежуточная пустая недельная сетка однажды прервала прогон; браузерный порт теперь ждёт загрузки карточек, и повторный полный прогон прошёл. Отдельная текущая неделя дала 18 занятий и успешную запись/чтение во временной базе. В рабочую базу эти данные не записывались: проект Supabase находится в `us-west-1`, документы оператора не утверждены, а правила автоматического доступа РАНХиГС не подтверждены.

На авторизованном аккаунте БИ 1.2 с кодом `Э-ОБ-385-04-26-02` браузерный пилот прочитал 20 занятий за 2–8 ноября 2026 и 74 карточки месячной сетки ноября 6 ноября; 74 карточки совпали с недельными представлениями. При повторной проверке 7 ноября источник показывал уже 71 карточку, и все 71 снова совпали с недельными сетками. Реальные 20 занятий были записаны и прочитаны обратно только во временной локальной SQLite БД. Это не импорт в рабочую базу StudGroup. Проверка неверного кода группы завершилась `identity_unverified`.

Локальный read-only прогон:

```bash
cd apps/backend
uv sync --frozen
uv run python -m playwright install chromium
uv run python scripts/ranepa_auth_readonly.py --group-code 'Э-ОБ-385-04-26-02' --week-start 2026-11-02 --month --local-db-check
```

Скрипт запрашивает логин и пароль без эха, не пишет HTML, cookies или секреты в репозиторий и обычно выводит лишь агрегаты. `--sdo` добавляет проверку ссылок без публикации. `--show-matches` вместе с `--sdo` локально выводит дату, предмет и подтверждённый чистый Moodle URL для отчёта владельцу; такой вывод не прикладывать к CI и PR. Временная БД удаляется после теста. Снимки экрана и страницы авторизованной сессии не прикладывать к PR.

`--http-check` после браузерного входа делает отдельный GET той же страницы обычным HTTP-клиентом с сессионными cookies только в памяти. В результате выводятся лишь HTTP-статус и признаки отрисованной недельной/месячной сетки. Реальный запуск 6 ноября 2026 дал HTTP 200, но обеих сеток в HTML не было; тот же браузерный прогон прочитал 20 занятий. Значит, прямой GET страницы недостаточен. Возможность использовать отдельный внутренний API без браузера не проверена.

Перед production-включением нужно проверить несколько аккаунтов разных подгрупп, добиться подтверждённого сопоставления СДО на реальных курсах, измерить время и память ограниченного worker, проверить миграцию и полный CI. Затем требуется отдельное согласие владельца на включение `RANEPA_CRAWL_ENABLED` и `RANEPA_SCHEDULE_VIEW_ENABLED`, развёртывание сервиса и изменение рабочего расписания.
