# Каталог предметов группы для C+ (контракт и точка интеграции для Codex)

Статус: реализовано на стороне C+ (задача №05). Реальный источник каталога — зона Codex
(`subjects.py`); сейчас каталог строится из того, что уже есть в БД.

## Как C+ определяет предмет

1. При постановке shadow-запуска (`shadow_worker.enqueue_shadow`) каталог группы кладётся в
   замороженный вход `AnalysisInput.subject_catalog` (без миграций; он не входит в
   `source_snapshot_sha256`, старые входы без него читаются как «каталога нет»).
2. Вызов Pass 2 (`cplus-extraction-8`) получает `user_payload.subject_catalog`
   (`id`, `name`, `aliases`, `teachers`, `complete`, `version`) рядом с сообщениями. Модель решает
   предмет **по смыслу** (тема, преподаватель в соседних сообщениях, как группа называет предмет) и
   возвращает `subject_id` и каноническое `subject`; при нехватке контекста — `null`.
   Дополнительных вызовов AI нет, Pass 1 не менялся.
3. Адаптер (`output_adapter.catalog_subject`) только проверяет выбор модели:
   - id есть в каталоге этой группы → подтверждено, `subject` заменяется на каноническое имя,
     `subject_source="catalog"` (это поле ставит только код, от модели оно не принимается);
   - id нет, но точное имя/алиас (после casefold, ё→е, пунктуации) однозначно совпало → подтверждено;
   - неизвестный id → не подтверждается (`subject_id_unknown`); неоднозначная метка →
     `subject_ambiguous`; предмет вне **полного** каталога → снимается (`subject_not_in_catalog`);
     вне **неполного** — остаётся прежняя текстовая проверка;
   - каталог другой группы или пустой игнорируется (`subject_catalog_ignored_*`), поведение прежнее.
4. `card_editor` не требует дословного упоминания для подтверждённого каталогом предмета и по-прежнему
   проверяет остальные предметы по тексту (`unsupported_subject`).
5. `resolver` записывает `edited_card.subject` (проверенный предмет), а не `proposal.subject`.
   При обновлении подтверждённый предмет заменяется только другим подтверждённым; пустой результат
   повторной обработки предмет не стирает.

Ничего про «ПИР», «матан» и т. п. в коде нет: это решает модель по контексту.

## Контракт `SubjectCatalog` (`analysis/contracts.py`)

```json
{
  "group_id": "<uuid группы>",
  "version": "<строка до 64 символов | null>",
  "complete": false,
  "subjects": [
    {"id": "<стабильный id, до 64 символов, уникален в каталоге>",
     "name": "<каноническое название>",
     "aliases": ["<подтверждённые сокращения, до 20>"],
     "teachers": ["<преподаватели, до 10>"]}
  ]
}
```

Не более 80 предметов. `complete=true` — только если источник гарантирует, что других предметов
у группы нет (тогда предмет вне каталога снимается). В других случаях `false`.

## Единая идентификация предметов (05A)

Одна формула на всех: `subject_id = uuid5(group_id, name.casefold())` — формула, по которой id строят все
писатели `main`. Реализация без зависимостей: `studgroup/subject_identity.py` (`subject_uuid`). Её используют:

- каталог C+ (`SubjectEntry.id` — строка с UUID);
- проекция карточки (`projection.py`: `Homework.subject_id`);
- ручные карточки старосты, импорт, `local_preview`, `processing`, `review_import`;
- студенческий API (`student_cards.py`, `subjects.py`): для предмета с карточками берётся
  `min(Homework.subject_id)`, для предмета без карточек — та же `subject_uuid`.

Правила контракта:

- в id не участвуют замена «ё→е», схлопывание или обрезка пробелов — только `casefold()`;
- мягкая нормализация (`match_key`, `label_key`: регистр, «ё→е», пунктуация, пробелы) разрешена только для
  поиска и сопоставления подписей, но не для построения id;
- похожие названия автоматически не сливаются: «Учёт» и «Учет» — два предмета с разными id; если подпись
  подходит нескольким предметам каталога, она «неоднозначна» и подтверждённого предмета не даёт;
- переименование даёт новый id; миграции id и слияния вариантов нет, для этого нужна отдельная стратегия;
- записи старых запусков с id вида `sched-…` читаются (поле — свободная строка), но в новых каталогах
  такого id нет, и в каталоге нового запуска он будет «неизвестным»;
- проверочный тест (`test_subject_identity.py`) запрещает вторую формулу в исходниках.

## Версионирование каталога (05A)

- Каталог — справочные данные, а не источник: он **не** входит в идентичность запуска
  `(raw_message, revision, generation)` и в `source_snapshot_sha256`. Поэтому обновление расписания не
  создаёт второй запуск и не порождает дубли карточек (повторная постановка возвращает существующий запуск).
- Что записывается: `metrics.subject_catalog = {present, fingerprint, version, complete, subjects}`;
  `fingerprint` — sha256 содержимого (порядок и поле `version` не влияют). `wave_results` показывает
  `subject_catalogs.runs_by_fingerprint` — несколько отпечатков в одной волне означают смену расписания.
- Завершённый запуск воспроизводим: каталог лежит в его замороженном `input_json`.
- Явный requeue (`backfill.requeue_failed`) обновляет каталог в `input_json` на текущий (сообщения не
  меняются); прежний исход с его отпечатком остаётся в `metrics.history`.

## Проверка подтверждённости

- id должен быть в каталоге **этой** группы (каталог чужой группы или пустой не используется);
- id и формулировка не расходятся: id рядом с точным названием/алиасом другого предмета каталога →
  `subject_id_mismatch`, предмет не назначается; неизвестное сокращение («матан») не расхождение;
- неполный каталог ничего не подтверждает «по умолчанию»: предмет вне него остаётся под текстовой
  проверкой;
- пустой/неудачный повторный результат не стирает подтверждённый предмет карточки.

## Что C+ делает сейчас вместо `subjects.py`

`analysis/subject_catalog.load_subject_catalog(db, group_id, facts)` — **единственная точка
подключения**. Сейчас: уникальные (по `subject_key`) `SchedulePattern.subject` группы (каноническая
запись — самое частое написание), преподаватели из `SchedulePattern.teacher`, алиасы и преподаватели
только из **verified** `GroupKnowledgeFact` этой группы; id — по формуле выше, `complete=false`,
`version` — хеш содержимого. Берутся все паттерны группы, а не только `valid_until >= сегодня`, как
в `/v1/subjects`: так старые сообщения не теряют предметы прошлых периодов.

   локальной копии `normalized` (значения уже совпадают).
