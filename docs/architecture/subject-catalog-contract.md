# Каталог предметов группы для C+ (контракт и точка интеграции для Codex)

Статус: реализовано на стороне C+ (задача №05). Реальный источник каталога — зона Codex
(`subjects.py`); сейчас каталог строится из того, что уже есть в БД.

## Как C+ определяет предмет

1. При постановке shadow-запуска (`shadow_worker.enqueue_shadow`) каталог группы кладётся в
   замороженный вход `AnalysisInput.subject_catalog` (без миграций; он не входит в
   `source_snapshot_sha256`, старые входы без него читаются как «каталога нет»).
2. Вызов Pass 2 (`cplus-extraction-8`) получает `user_payload.subject_catalog`
   (`id`, `name`, `aliases`, `teachers`, `complete`, `version`) рядом с сообщениями. Модель решает
   предмет **по смыслу** (тема, преподаватель в соседних сообщениях, как группа называет предмет) и
   возвращает `subject_id` и каноническое `subject`; при нехватке контекста — `null`.
   Дополнительных вызовов AI нет, Pass 1 не менялся.
3. Адаптер (`output_adapter.catalog_subject`) только проверяет выбор модели:
   - id есть в каталоге этой группы → подтверждено, `subject` заменяется на каноническое имя,
     `subject_source="catalog"` (это поле ставит только код, от модели оно не принимается);
   - id нет, но точное имя/алиас (после casefold, ё→е, пунктуации) однозначно совпало → подтверждено;
   - неизвестный id → не подтверждается (`subject_id_unknown`); неоднозначная метка →
     `subject_ambiguous`; предмет вне **полного** каталога → снимается (`subject_not_in_catalog`);
     вне **неполного** — остаётся прежняя текстовая проверка;
   - каталог другой группы или пустой игнорируется (`subject_catalog_ignored_*`), поведение прежнее.
4. `card_editor` не требует дословного упоминания для подтверждённого каталогом предмета и по-прежнему
   проверяет остальные предметы по тексту (`unsupported_subject`).
5. `resolver` записывает `edited_card.subject` (проверенный предмет), а не `proposal.subject`.
   При обновлении подтверждённый предмет заменяется только другим подтверждённым; пустой результат
   повторной обработки предмет не стирает.

Ничего про «ПИР», «матан» и т. п. в коде нет: это решает модель по контексту.

## Контракт `SubjectCatalog` (`analysis/contracts.py`)

```json
{
  "group_id": "<uuid группы>",
  "version": "<строка до 64 символов | null>",
  "complete": false,
  "subjects": [
    {"id": "<стабильный id, до 64 символов, уникален в каталоге>",
     "name": "<каноническое название>",
     "aliases": ["<подтверждённые сокращения, до 20>"],
     "teachers": ["<преподаватели, до 10>"]}
  ]
}
```

Не более 80 предметов. `complete=true` — только если источник гарантирует, что других предметов
у группы нет (тогда предмет вне каталога снимается). В других случаях `false`.

## Что C+ делает сейчас вместо `subjects.py`

`analysis/subject_catalog.load_subject_catalog(db, group_id, facts)` — **единственная точка
подключения**. Сейчас: уникальные `SchedulePattern.subject` группы (каноническая запись — самое частое
написание), преподаватели из `SchedulePattern.teacher`, алиасы и преподаватели только из
**verified** `GroupKnowledgeFact` (`subject_alias`, `subject_teacher`) этой группы; id =
`sched-<sha1(нормализованное имя)[:12]>`, `complete=false`, `version` — хеш содержимого.

## Что осталось подключить Codex

1. Заменить тело `load_subject_catalog` на вызов модуля предметов: стабильные id предметов
   (а не `sched-…`), авторитетный `complete`, `version`, подтверждённые алиасы.
2. Если нужны id в карточке: `CanonicalAcademicItem` хранит только `subject` (строка), колонки
   `subject_id` нет — нужна миграция (зона Codex). Сейчас предмет сохраняется каноническим
   названием из каталога, `subject_id` живёт в сохранённом результате запуска.
3. Проекция в студенческий API (`projection.py`) строит `subject_id` через `uuid5(group, имя)`;
   после появления настоящих id её нужно перевести на них.
4. Подтвердить, что `complete=true` допустим для групп, у которых расписание загружено целиком.

Студенческий API, frontend, миграции, дедлайны и пакетная обработка не менялись.
