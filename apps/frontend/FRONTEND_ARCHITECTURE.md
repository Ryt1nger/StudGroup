## 1. Резюме и рекомендация

- **Стек подтверждён владельцем (Q0):** pnpm, React, TypeScript strict, Vite, React Router, TanStack Query, Zod только на недоверенных runtime-границах, CSS Modules + CSS custom properties, Vitest, React Testing Library, MSW, Playwright, ESLint + Prettier. Telegram — через официальный `window.Telegram.WebApp` за собственным адаптером, сторонний Telegram SDK не используется.
- Приложение — **SPA на Cloudflare Pages**; с FastAPI общается только через **сгенерированный из OpenAPI клиент**. Ни одного рукописного API-типа.
- **Единственная точка касания Telegram** — тонкий адаптер. Mock-адаптер не попадает в production (проверка в CI).
- Slice 1 live: bootstrap → «Сегодня» (только карточки `homework`) → детали ДЗ → действие «Источник». Навигация из четырёх пунктов: **Сегодня · Задания · Расписание · Предметы**. Неподключённые разделы — честное «Раздел готовится».
- Учебные данные живут **только в памяти запуска**: ни `localStorage`, ни IndexedDB, ни Service Worker Cache.
- **Порядок:** сейчас завершаются только документы Stage 0. Реализация стартует после получения макетов/ассетов и согласования контракта Slice 1 (подробно — §14). Открытые вопросы — §13.1.

## 2. Стек

### 2.1 Что выбрано и почему

| Область | Решение | Причина |
| --- | --- | --- |
| UI | React, TypeScript `strict` | Baseline brief; совместимо с генерацией типов из OpenAPI |
| Сборка | Vite | Быстрый HMR, простая сборка под Cloudflare Pages, нативные ESM |
| Роутинг | React Router (declarative/library-режим) | Данные приходят через TanStack Query, загрузчики роутера не нужны |
| Серверное состояние | TanStack Query | Кэш, ретраи, дедупликация, статусы запросов, refetch на возврат в приложение |
| Клиентское глобальное состояние | **нет** (React state + context для Telegram/сессии) | brief: без Redux без доказанной нужды |
| Стили | CSS Modules + CSS custom properties | Токены тем без рантайма, предсказуемо в слабых WebView |
| Условные классы | `clsx` | Baseline |
| Рантайм-валидация | Zod **только** на непроверяемых границах (например, `start_param`, query-параметры, ответы mock-сценариев). Ответы API валидирует тип-генерация | Не дублировать контракт |
| API-клиент | Генерируется `@hey-api/openapi-ts` из `packages/contracts/openapi.yaml` в `packages/shared-types` | Baseline; генератор — кандидат, окончательно подтверждает Codex |
| Форматирование дат | Нативный `Intl` | Часовой пояс группы, русская локаль |
| Шрифт | **Inter, локально** (решение владельца): исходные файлы из пакета ассетов, если они будут; иначе пакет вариативный `@fontsource-variable/inter` (ось wght; веса 650/750 из §6.3; subset latin + cyrillic, `font-display: swap`). Внешний Google Fonts CDN в production не используется | Корректная кириллица, нет внешних запросов из WebView; лицензия OFL |
| Иконки | SVG-спрайт/компоненты из дизайнерского набора (ждём ассеты) | Не растр и не иконочный фреймворк «на всякий случай» |
| Тесты | Vitest, React Testing Library, user-event, jest-dom, MSW, Playwright | Baseline |
| Доступность | `axe-core` в Playwright и/или `vitest-axe` | Добавление к baseline |
| Качество | ESLint (+ `typescript-eslint`, `react-hooks`, `jsx-a11y`), Prettier, `tsc --noEmit`, `vite build` в CI | Baseline + a11y-lint |

### 2.2 Дополнения к baseline (подтверждены владельцем в рамках Q0, кроме п. 5 — он уточняется после замера)

1. **Пакетный менеджер: pnpm + workspaces** (подтверждено) (`apps/frontend`, `packages/shared-types`). Нужно, чтобы frontend импортировал сгенерированный пакет как workspace-зависимость. Если Codex уже зафиксировал другой менеджер в CI — подстроюсь; нужен один lockfile на монорепо.
2. **Node.js — актуальный LTS**, закрепить в `.nvmrc`/`engines`. Версии пакетов: актуальные стабильные на момент scaffold, **закрепляются lockfile**; плавающих версий в CI нет (требование brief). Конкретные номера я не фиксирую в этом документе, чтобы не выдумывать их по памяти; они будут выбраны и проверены при scaffold.
3. **Свои минимальные TypeScript-декларации для `window.Telegram.WebApp`** (только используемое подмножество) внутри слоя адаптера. Это не API-модель StudGroup, а описание внешнего SDK, поэтому правило «без дублирующих API-типов» не нарушается. Альтернатива — сторонний пакет типов; я предпочитаю не добавлять зависимость ради ~30 строк.
4. **Telegram SDK-обёртки (`@telegram-apps/*` и подобные) не используются** — brief требует официальный скрипт и один тонкий адаптер.
5. **Размерный бюджет (предложение):** начальный JS-чанк заранее ограничен и проверяется в CI; точное число предлагаю зафиксировать после первого scaffold-замера, а не придумывать сейчас. Роуты prepared-разделов и экран деталей — отдельные lazy-чанки.
6. **Без анимационных библиотек** (как в brief). Переходы — CSS, уважают `prefers-reduced-motion`.

**Правила границ (проверяются ESLint `no-restricted-*` и ревью):**
1. `window.Telegram` и `Telegram.WebApp` — только в `platform/telegram/*`.
2. Сгенерированный клиент импортируется только из `src/api/*`; features используют хуки из `api/hooks`.
3. `ui/*` не знает про домен StudGroup (ни `Event`, ни `Homework`); доменные отображения — в `features/*` и `ui/badges/*`.
4. Рукописные интерфейсы request/response запрещены; ESLint-правило/CI-grep запрещает объявлять типы с именами ответов API вне `shared-types`.
5. `localStorage`/`sessionStorage`/IndexedDB для токенов и учебных данных не используются (§8, §10).

## 4. Карта маршрутов

Bootstrap/gate-логика выполняется **до** роутера: пока сессия не получена, роуты не монтируются.

| Маршрут | Экран | Статус | Примечание |
| --- | --- | --- | --- |
| `/` | redirect → `/today` | live | учитывает `start_param` (deep link) |
| `/today` | Today | **live (ДЗ)** | |
| `/events/:eventId` | Детали карточки | **live (только `homework`)** | Generic-id в домене — `Event`; экран выбирается по `type` из ответа; неизвестный `type` → честное «не поддерживается в этой версии», без догадок |
| `/tasks` | Раздел «Задания» | реализован (контракт 0.3.0, `GET /homework`, серверные фильтры, курсоры; см. DESIGN_HANDOFF §13) | название утверждено (Q3); «Дедлайн» — свойство, фильтр или блок, но не название раздела |
| `/schedule` | Расписание | prepared | |
| `/subjects` | Предметы | prepared | |
| `*` | NotFound | live | |

Состояния, **не являющиеся маршрутами** (рендерятся Bootstrap/Boundary поверх или вместо контента): загрузка, нет активной группы, не участник Telegram-группы / `suspended`, группа не авторизована для пилота, приглашение просрочено/использовано, `deletion_pending`, backend недоступен, офлайн.

Действие «Источник» — **не маршрут**: кнопка в деталях → `openTelegramLink` либо inline-блок/bottom sheet «Источник недоступен» с причиной.

**Deep link из сообщения бота** (UX-правило PDF v0.3: клик ведёт сразу в карточку): через `start_param` → `/events/:eventId`. Формат параметра задаёт backend/bot (Codex); frontend парсит его по контракту, считает **недоверенным** навигационным подсказчиком и не использует для авторизации. См. требование CR-DEEPLINK.

Нижняя навигация (утверждено, Q3/Q10): **Сегодня · Задания · Расписание · Предметы**. Пункта «Ещё», живого «Спросить AI», общего персонального AI-чата и ложных переходов в неработающие функции в первом срезе **нет**. Неподключённые разделы ведут на `PreparedSection` с текстом «Раздел готовится»; ни вымышленных данных, ни счётчиков.

Telegram `BackButton`: показывается на `/events/:eventId` (и вложенных), скрыт на корневых вкладках; внутри приложения собственной стрелки «назад» нет.

## 5. Дерево компонентов и зоны ответственности

```text
<TelegramAppProvider>              платформа: adapter, тема, viewport, safe-area, BackButton
  <ApiClientProvider>              клиент + QueryClientProvider + cachePolicy
    <ThemeProvider>                data-theme по adapter.colorScheme, токены
      <AppBootstrap>               запрос session; решает: loading | gate | ready
        ├─ <BootstrapLoading/>
        ├─ <AccessGate kind=…/>    no_group | not_member | group_not_authorized
        │                          | invite_expired | invite_consumed | deletion_pending …
        └─ <SessionBoundary>       session в контексте: group, role, permissions, timezone
             <RouterProvider>
               <AppShell>          TopBar + <Outlet/> + BottomNav
                 <RouteErrorBoundary>
                   /today        → <TodayScreen/>
                   /events/:id   → <EventDetailScreen/>
                   /subjects…    → <PreparedSection/>
```

### Слои и ответственность

| Модуль | Ответственность | Не отвечает за |
| --- | --- | --- |
| `TelegramAppProvider` / adapter | `initData` (сырая строка), тема, viewport/safe-area, BackButton, openLink, haptics (если есть), версионные проверки | авторизацию, бизнес-логику |
| `AppBootstrap` / `SessionBoundary` | первичный запрос сессии, выбор экрана-«ворот», доставка group/role/permissions/timezone | вывод прав из «роли» |
| `api/*` | клиент, ключи, кэш-политика, retry, маппинг ошибок, `server_time` offset | рукописные модели |
| `AppShell` | шапка, нижняя навигация, safe-area, фокус-менеджмент при смене маршрута | данные |
| `features/today` | Today-лента, карточка ДЗ, пустая/частичная/ожидание обработки | расчёт срочности/уверенности |
| `features/event-detail` | детали ДЗ, секции, «выполнено мной» (когда будет в контракте) | права старосты (только отображение флагов backend) |
| `features/source` | действие источника, объяснение недоступности | построение ссылок (даёт backend) |
| `ui/badges/*` | Status / Urgency / Confidence / Source — **четыре независимых компонента**, исчерпывающие `switch` по enum контракта + fallback для неизвестного значения | слияние состояний с одинаковым цветом |
| `ui/StateScreen` | единый шаблон empty/offline/permission/error | выбор причины |

**Принципы:**
- Состояния **не схлопываются**: разные коды контракта → разные компоненты/тексты, даже если цвет близок.
- Каждый enum-бейдж имеет явный `default`-ветку: неизвестное значение показывается нейтрально («Неизвестный статус») и логируется как предупреждение, не ломая экран. Это даёт обратную совместимость, о которой говорит ADR/Module 1.
- Порядок элементов ленты определяет backend; frontend **не пересортировывает** по собственной «срочности».
- Права берутся только из `permissions` ответа; `role` — для подписи.

## 6. Дизайн-токены

Решение владельца (ревизия 5): значения ниже **утверждены** и заменяют декларацию бренд-листа и оценки по растру. Палитра PDF v0.3 по-прежнему не используется. Реализуются как семантический слой CSS custom properties; примитивы — по необходимости.

### 6.1 Слои
1. **Примитивы** (`--sg-primitive-*`): не используются в компонентах напрямую.

4. **Telegram/viewport**: `--sg-safe-*`, `--sg-viewport-height`, `--sg-viewport-stable-height` — выставляются адаптером.

## 7. Telegram-адаптер

### 7.1 Интерфейс (набросок; детали стабилизируются при реализации)
```ts
interface TelegramAdapter {
  readonly kind: 'telegram' | 'mock';
  ready(): void;                       // WebApp.ready()
  expand(): void;
  getInitData(): string;               // СЫРАЯ строка initData для backend; пустая → «не в Telegram»
  getStartParam(): string | undefined; // только для навигации, недоверенный
  colorScheme(): 'light' | 'dark';
  onThemeChange(cb): Unsubscribe;
  viewport(): { height: number; stableHeight: number; safeArea: Insets };
  onViewportChange(cb): Unsubscribe;
  backButton: { show(cb): void; hide(): void };
  openLink(url: string): void;         // внешние http(s)
  openTelegramLink(url: string): void; // t.me
  haptic?(kind): void;
  isVersionAtLeast(v: string): boolean;
  platform(): string;
}
```

### 7.2 Правила
- Официальный скрипт `telegram-web-app.js` подключается в `index.html` **до** бандла; при его отсутствии (обычный браузер без mock) приложение показывает контролируемый экран «Откройте приложение в Telegram», а не падает.
- В backend уходит **только** `initData` (сырая строка). `initDataUnsafe` для аутентификации/авторизации **не используется**. Токены бота/секреты в клиенте отсутствуют и не могут появиться (`.env` с префиксом `VITE_` содержит только публичные значения; CI-проверка на подозрительные имена).
- `start_param` читается для навигации, как подсказка; backend повторно проверяет доступ к карточке.
- Новые возможности Telegram (safe-area, отключение вертикального свайпа и др.) используются **только после** `isVersionAtLeast`, иначе — fallback на CSS `env()` и без них. Точные версии API я сверю с официальной документацией Telegram (<https://core.telegram.org/bots/webapps>) при реализации адаптера — здесь не утверждаю.
- Внешние ссылки: перед `openLink` — проверка схемы (`http`/`https`), `javascript:`, `data:` и подобные блокируются; ссылки на `t.me` идут через `openTelegramLink`.
- Тема: `data-theme` по `colorScheme` Telegram, подписка на `themeChanged`; **ручного переключателя в Slice 1 нет (Q9)**; цвета — наши токены; `themeParams` — только для шапки/фона окна WebView (по решению Q9).

### 7.3 Mock-адаптер для обычного браузера
- Реализует тот же интерфейс; даёт настраиваемые `colorScheme`, viewport/safe-area, `initData` — **явно недействительную фиксированную строку**, которую backend обязан отклонить.
- Включается **только** если одновременно: сборка dev/test **и** явный флаг (`VITE_TELEGRAM_MOCK=true` или query `?mock=1`, обрабатываемый только в dev). Подгружается через динамический `import()` под compile-time условием, которое Vite выкидывает из production.
- **CI-страховка:** шаг после `vite build` ищет в `dist/` маркер mock-адаптера и падает, если находит.
- Сценарии (тема, пусто/ошибка/офлайн/нет доступа) переключаются в dev через MSW-хэндлеры, построенные на **примерах контракта**; в production-сборке нет MSW.

## 8. Сессия, авторизация, кэш

Всё, что касается semantics токена, — решение backend (CR-AUTH). Предлагаю frontend-сторону:

- Bootstrap: `POST`(по контракту) c сырой `initData` → ответ с сессией. Токен/сессионный артефакт хранится **в памяти**; не в `localStorage`. При истечении — повторный запрос с `initData` (если `initData` ещё допустим по правилам backend), иначе экран «Откройте приложение заново из Telegram».
- Cloudflare Pages и FastAPI на **разных origin**: нужны CORS-политика backend и CSP на frontend (`connect-src` только API-origin). Cookie-схема в Telegram-WebView ненадёжна из-за третьесторонних cookie; рекомендую bearer-токен — но решение за Codex.
- **Кэш-политика (`cachePolicy.ts`)**: Today — короткий `staleTime`, refetch при возврате видимости и при `online`; detail — по ключу `eventId`+`revision`; `retry` только для сетевых ошибок и 503/«повторяемо» (по полю контракта), **не** для 4xx; экспоненциальная пауза; учитывается `Retry-After`, если есть в контракте.
- **Персистентного кэша нет (решение владельца).** Учебные данные не сохраняются между запусками ни в `localStorage`, ни в IndexedDB, ни в Service Worker Cache; TanStack Query держит их только в памяти текущего запуска (`persistQueryClient` не подключается, Service Worker не регистрируется). После закрытия WebApp данные загружаются заново. Причина: Module 0 §14 требует полного удаления учебных данных по `delete_at`. Нечувствительные интерфейсные настройки можно хранить отдельно только после явного согласования. Проверка в CI: grep на `localStorage|sessionStorage|indexedDB|serviceWorker|caches.` в `src/` с явным allowlist.
- «Устаревшие данные» (остаются в памяти текущего запуска): данные считаются потенциально устаревшими, если с последнего **успешного** обновления прошло **более 15 минут** (Q12). Текст: «Данные могли устареть · обновлено в 12:30» (время — в часовом поясе группы, от `generated_at`; «15 минут» считаем по серверному времени с offset из `server_time`, не по часам устройства). Порог — константа в `cachePolicy.ts`.
- **Polling обработки (Q16).** Пока `processing.state ≠ idle/none`: повторный запрос через **10 с**, затем интервал **30 с**; через **10 минут** автоматический polling прекращается и показывается кнопка **«Проверить снова»** (ручной refetch). Состояние `delayed` устанавливает только backend; frontend сам «задержку» не вычисляет. Таймеры сбрасываются при уходе экрана и при `visibilitychange: hidden`.
- Контент описаний и названий — **только текст** (никакого `dangerouslySetInnerHTML`); AI/пользовательский текст не интерпретируется как разметка.

## 11. Требования к backend / OpenAPI (для Codex)

Это **требования к контракту**, а не предложения по реализации. Названия операций и полей — на усмотрение Codex; важно содержание. Всё, чего нет в Slice 1, должно быть **optional/nullable** и не заполняться frontend'ом самостоятельно.

### CR-GENERAL — общие
1. Единый формат идентификаторов и **ISO 8601 с явным offset/UTC**; часовой пояс группы (IANA) отдаётся рядом.
2. Каждый ответ списка/детали содержит `generated_at`; сессия — `server_time` (для расчёта offset часов).
3. Все enum — **закрытые в документации, но клиент обязан терпеть неизвестные значения**; добавление значения — совместимое изменение; удаление/переименование — breaking.
4. Любое поле, которое может быть неизвестным, имеет явное представление «unknown», а не `""`/`0`/`null` без семантики.
5. Единая схема ошибки: машинный `code`, `message` (безопасный), `correlation_id`, `retryable` (bool), `retry_after_seconds` (если есть), для ошибок валидации — путь поля. Коды различают как минимум: `unauthenticated`, `initdata_invalid`, `initdata_expired`, `permission_denied`, `not_found`, `gone`, `no_active_group`, `not_group_member`, `membership_suspended`, `group_not_authorized_for_pilot`, `invitation_expired`, `invitation_consumed`, `group_deletion_pending`, `rate_limited`, `service_unavailable`, `internal_error`. Каждый — с примером.
6. Примеры запросов/ответов для **каждого** состояния (empty, partial, needs_clarification, unknown deadline, imported source, source unavailable…) — frontend строит из них MSW-моки.

### CR-AUTH — аутентификация и сессия
1. Операция bootstrap принимает **сырую `initData`**; ответ — сессионный артефакт и сессия (ниже).
2. Явно описать: тип и срок жизни токена, как продлевается, как передаётся (заголовок/cookie), требования CORS. Желателен bearer в заголовке (см. §8).
3. Описать поведение при просроченной `initData` (`auth_date`) — код ошибки и можно ли ретраить.

### CR-SESSION — данные bootstrap
- `user`: `id`, отображаемое имя (для инициала аватара), без фото-URL в Slice 1 (если не требуется).
- `membership`: `status` (`active` / `suspended` / `left`), `role` (`student` / `headman` / `deputy`), для `suspended` — время следующей проверки и доступно ли действие «перепроверить».
- `group`: `id`, название, `timezone` (IANA), `status` (`active` / `deletion_pending` / read-only-подписка и т. п.), `pilot_authorized`.
- `permissions`: **список/карта разрешённых действий** на уровне группы (авторитетные). Frontend не выводит права из `role`.
- `server_time`.
- Если активной группы нет — **не 500**, а определённое состояние/код (`no_active_group`).

### CR-TODAY — лента «Сегодня»

1. **Состав ленты (решение владельца Q1).** В первом срезе — только реальные карточки `homework`. Карточка входит в ленту, если выполняется **хотя бы одно** условие:
   1. дедлайн сегодня;
   2. отменённые и с прошедшим сроком исключены: доступны в архиве «Заданий»;
   3. карточка создана или существенно изменена за последние 24 часа;
   4. одно из трёх ближайших заданий с дедлайном в пределах семи дней.

   Порядок: с дедлайном сегодня; новые или изменённые; ближайшие предстоящие. Архивные исключены даже после недавней правки. **Одна карточка не дублируется в нескольких секциях.** Backend определяет выборку; frontend дополнительно скрывает карточку при наступлении срока по живым серверным часам. Дата без времени остаётся актуальной весь календарный день группы.
   - **Выполнено мной.** Убирает карточку из «Сегодня», даже после существенной новой ревизии. Личная отметка сохраняется; сведения об обновлении доступны в деталях и списке «Задания»/архиве.
   - **«Существенно изменена» определяет backend (Q13):** дедлайн, отмена, дата, время, место, ссылка, формат. Frontend получает готовый булев признак и не сравнивает ревизии.
2. **Контракт расширяем через секции.** Ответ — упорядоченный список секций; секция имеет стабильный машинный `kind` и `items[]`. Во Slice 1 определены секции для четырёх условий (рабочие имена: `overdue`, `due_today`, `new_or_changed`, `upcoming`); в следующих срезах добавятся следующая пара, переносы, отмены, объявления и т. д. Клиент **пропускает неизвестные секции и неизвестные `type`** с предупреждением в логе и не рисует догадок. Заголовки секций формирует frontend по `kind` из каталога копирайта (утверждает владелец).
3. Ответ: `generated_at`, `group_timezone`, `sections[]`, признак пустоты ленты (без секций с пустыми заголовками), пагинация/курсор, если применима, `freshness`, **feed-level `processing`** (см. п. 5).
4. Элемент `homework` (минимум для карточки):
   - `id`, `type`, `title`, `subject` (`id`, `name`; не строка-дубликат), `summary`;
   - `deadline`: `{ state: known | unknown, at?: ISO, date_only?: bool }`;
   - `status` — студенту возвращаются только опубликованные состояния (Q6): `detected` и `incomplete_hidden` frontend **не получает**. Набор остальных значений (`needs_clarification` / `published` / `completed` / `cancelled`) и их показ — Codex в схеме;
   - `urgency` (Module 0 §12; имена enum — Codex);
   - `visibility`: `hidden` / `staff_only` / `group` / `personal` (Q6). Студент получает **только** `group` и `personal`; остальные не приходят, а при получении клиент их игнорирует;
   - **Без числовой уверенности AI и без номера `revision` для показа студенту (Q7).** Вместо них — явные поля статуса: `confirmation{kind}` (Q17), `needs_clarification` и т. п. `revision` остаётся служебным (`expected_revision` для записи, ключ кэша) и в UI не выводится; `confidence_band` как отдельное поле для UI не требуется;
   - `source`: `kind`, `availability`, `imported`, дата сообщения (см. CR-SOURCE);
   - `processing` на уровне карточки (см. п. 5);
   - `created_at`, `updated_at`, и **признак «существенно изменена»** (или поле, из которого он выводится на backend; frontend не гадает — Q13);
   - `my_state`: `{ done: bool, done_at? }` — личное «Выполнено мной» (Q8, Q19), **обязательно во Slice 1**;
   - `changed_after_my_completion` (bool) — Q14;
   - `significant_change` (bool) — Q13;
   - `source_label`: `group` / `imported` (метка на карточке списка, Q18; подписи «Из группы» / «Импортировано»).
5. **Состояния обработки (решение владельца Q4).** Студенту **не показываются** техническая формулировка «AI обрабатывает» и название DeepSeek. Контракт должен позволять различить:
   - **feed-level** `processing.state`: `idle` / `updating` (карточки ещё нет, идёт обновление группы — UI: нейтральный индикатор «Обновляем информацию группы») / `delayed` (UI: «Обработка информации задерживается. Данные появятся автоматически»). Фиктивная или пустая карточка **не создаётся**;
   - **card-level** `processing.state`: `none` / `reanalyzing` (UI: последняя подтверждённая версия + компактный статус «Проверяем обновление»; незавершённый результат данные **не заменяет**) / `delayed`;
   - технических причин, имён провайдеров, текстов ошибок AI в ответе студенческого API **нет**.
   
   Автоматическое появление/обновление карточки: во Slice 1 — через **периодический refetch только пока `processing.state ≠ idle/none`** (рекомендуемый интервал и верхний предел попыток — запросить у Codex; WebSocket/SSE не нужны по Module 1 §4 п. 7). Системное уведомление владельцу при задержке — ответственность backend, на frontend не влияет.
6. Блоки будущих секций (ближайшая пара, изменения) во Slice 1 **не возвращаются** с фиктивными данными.

### CR-DETAIL — детали карточки
Всё из карточки плюс: полное `description`; `subject`; `deadline`; `status`; `confirmation`; служебная `revision` (только для записи); `evidence`/`source` summary; `permissions` на уровне карточки (что доступно текущему пользователю: сейчас — просмотр; потом — действия старосты/заместителя); опциональные и пока пустые `attachments[]`, `history[]` (revision summary), `report_error` capability, `my_state`. Для удалённой по ретеншну карточки — отличать `gone` от `not_found` (Module 0 §14).

Уточнения по макетам (ревизия 3):
1. **Срок**: `deadline` — объединение `known{at, date_only}` / `unknown`; макет показывает «Срок не указан» / «Дата уточняется» с плашкой «Информация уточняется». Клиент не выводит «неизвестно» из `null` сам.
2. **Статусы и «Подтверждено»** (Q17, решено): «Подтверждено» — **только** ручное подтверждение старостой или заместителем (`confirmation.kind = manual`). Автоматическая публикация по сообщению группы получает статус «Из сообщения группы» (`confirmation.kind = from_group_message`). Бейдж строится из явного поля контракта, а не из `status`/`confidence`; клиент никогда не выводит «Подтверждено» самостоятельно. Показ при неизвестном `kind` — без бейджа.
3. **Дата получения**: `source.message_date` (+ `received_at`) для строки «Получено …».
4. **Во Slice 1 скрыты**: «Материалы» (`attachments[]`), «История изменений» (`history[]`), «Сообщить об ошибке», «⋯», кнопка-календарь, «Добавлено преподавателем», чип «Практика» (Q21). Поля остаются опциональными; клиент их не требует.
5. **Типы** «Проект» и «Презентация» (Q20, решено): отдельных доменных типов нет; для первого MVP это разновидности `homework` (расширение классификации отложено). Клиент отображает чип «ДЗ»; неизвестный `type` — нейтральный чип без падения.

### CR-SOURCE — источник и действие

**«Источник недоступен» — нормальное состояние, не ошибка приложения (решение владельца).** Карточка продолжает отображаться; вместо активной кнопки показывается текст **«Источник недоступен»**. Контракт должен отдавать безопасную информацию, которую можно показать и при недоступности:

1. `source.kind` — тип источника (сообщение группы / прямое сообщение старосты боту / импорт истории / иное по документам);
2. `source.message_date` — дата сообщения;
3. `source.imported` — импортирован ли источник (D3: ссылка опциональна);
4. `source.excerpt` — доступный текстовый фрагмент (опционально), с лимитом длины и правилом, когда его можно показывать;
5. `source.availability` — доступен / недоступен **с машинной причиной** (`retention_expired`, `no_deep_link`, `message_deleted`, `no_access` и т. п.; набор — Codex). Причина влияет на подпись, но не превращает экран в ошибку; текст для каждой причины утверждает владелец;
6. **Метаданные действия**: `action.type` (`open_telegram_link` / `none`), готовый `url` (строит backend; frontend ссылку не конструирует) — **только** когда доступен.

Учитывать Module 0 §14: исходный текст живёт 30 дней, карточка — минимум 90, поэтому недоступность по сроку хранения — штатный случай.

### CR-DEEPLINK — deep link
Формат `start_param` для перехода к карточке из сообщения бота (кодировка, ограничения длины, подпись/идентификатор, поведение при отсутствии доступа). Frontend считает его недоверенным.

### CR-INVITE — активация по приглашению (решение владельца Q2)

Приглашения в первом срезе обрабатываются **только через Telegram-бота**; WebApp-интерфейса управления приглашениями нет. Сценарий: староста выполняет `/connect` → открывает личный чат с ботом → «Пригласить студентов» → бот создаёт пакет одноразовых ссылок (одна группа, 24 часа, одна активация) → студент открывает ссылку → backend проверяет членство → бот предлагает открыть WebApp.

Для WebApp это означает: **HTTP-операций приглашений нет**; из состояний, перечисленных в brief §5, приглашение «просрочено/использовано» отображает бот, а WebApp показывает только «Нет активной группы» (и состояния членства `suspended`/`left`, если backend их отдаёт). Прошу Codex подтвердить, что сессия не возвращает отдельных invite-кодов ошибок (иначе — добавить в схему ошибок). Отказ неподключённой пилотной группе обрабатывает **бот**; отдельного экрана `group_not_authorized_for_pilot` в WebApp **нет** (Q15), без группы показывается «Нет активной группы».

### CR-PERSONAL — «Выполнено мной» (Slice 1, решение Q8, Q14, Q19)
«Выполнено мной» — **реальное персональное действие**: можно отметить и **отменить** отметку. Требования к контракту:
1. Две идемпотентные операции (или одна с булевым значением): отметить / снять отметку для текущего пользователя и карточки; повтор не ошибка.
2. Запрос с `expected_revision` (или иным токеном версии); при конфликте — машинный код (`revision_conflict`) и актуальная карточка в ответе.
3. Ответ возвращает обновлённые `my_state`, `changed_after_my_completion` и, если нужно, актуальную карточку — **frontend не пересчитывает** группировку ленты сам; ключ Today инвалидируется.
4. Личное состояние **не меняет** групповой `status`; доступность операции — по `permissions` карточки/группы (в т. ч. для `cancelled`, `needs_clarification`, `membership` не `active`).
5. Для `my_state` и записи — коды ошибок из CR-GENERAL (`permission_denied`, `gone`, `rate_limited`, …).
6. Поведение клиента (по макету): оптимистичный переход, откат при ошибке с понятным сообщением; везде подпись «Выполнено мной»; карточка в Today после отметки исчезает; при возврате — пометка «Изменено после выполнения».

### 12.2 Критические E2E (против согласованного тестового backend)
1. **Happy path:** запуск (mock-адаптер dev / тестовый `initData` в стенде) → bootstrap → Today показывает реальную карточку ДЗ → открытие деталей → действие «Источник» вызывает `openTelegramLink` с URL из контракта.
2. Пустая лента.
3. Карточка `needs_clarification` / unknown deadline.
4. `permission_denied` и `no_active_group` → корректные gate-экраны.
5. Backend 503 → «Повторить» → успех.
6. Офлайн (Playwright `context.setOffline`) → показ состояния и восстановление.
7. Источник недоступен (импорт/ретеншн): карточка остаётся, кнопки нет, безопасные поля видны.
7a. Три режима обработки (updating / reanalyzing / delayed) и автоматическое появление карточки через refetch.
8. Темы light/dark: одинаковые данные и структура.

### 16.5 Расписание (контракт 0.2.0, commit f51bd04)

**Подключено.** `/schedule` вызывает сгенерированный `getSchedule` (`start`/`end`, понедельник–воскресенье текущей недели в часовом поясе группы). Окно выбирается при открытии экрана по часам устройства (выбор недели, не срочность); «сейчас» для состояний пары берётся с сервера (`generated_at`). Показываются только поля контракта: `subject`, время, `location`, `teacher`; бейдж «Сейчас» вычисляется по `starts_at`/`ends_at`. `selected_week` даёт подпись «Первая/Вторая неделя»; `week_state = needs_clarification` показывается баннером «Расписание уточняется» (пары с чередованием backend пропускает). Запрос не выполняется без `schedule.read` в сессии (экран «Нет доступа к расписанию»); 403/5xx/офлайн/пустая неделя обработаны. Маппер: `src/features/schedule/mapSchedule.ts`; собственных API-типов нет.

**Не показывается, так как поля нет в контракте:** тип занятия (лекция/практика), бейджи «Подтверждено/Перенесено/Отменено» (в `status` пока только `scheduled`), цвет и иконка предмета, вкладки «Моё/Группы», переход к неделям (кнопки «назад/вперёд» не добавлены).

**Блок «Ближайшая пара» на «Сегодня» (контракт 0.2.1, commit e8c99c2).** `NextClassCard` подключён к `today.next_lesson`: `state=current` → «Идёт сейчас», `upcoming` → «Следующая пара» с «Через N мин / ч», «Завтра» или датой (относительное время считается от серверного «сейчас»); `null` → карточка не рендерится. `empty` относится только к заданиям и карточку не скрывает (покрыто тестом). Нажатие открывает `/schedule`. Маппер: `mapNextLesson.ts`.

**Недели и время.** Начальная неделя `/schedule` выбирается по `session.server_time` в часовом поясе группы; время сессии привязано к монотонным часам (`performance.now`), поэтому неверная дата телефона на неё не влияет. Тесты с телефоном «2024-02-01» при серверной дате 2026-10-14: неделя 2026-10-12…18 и «Через 30 мин» для пары. Тест неделя-по-серверному-времени падает при возврате к `Date.now()`.

# Переключение «Сегодня / Завтра» (контракт 0.4.1)

Заголовки — кнопки с `aria-pressed`; активный день остаётся единственным h1,
он крупнее и ярче. День хранится в URL (`/today?day=tomorrow`) и отдельном
ключе запроса; изменения личного выполнения инвалидируют оба дня.
Завтра запрашивается через сгенерированный `getToday({query: {day: 'tomorrow'}})`.
Backend выбирает следующую календарную дату группы и только её известные
дедлайны и первую пару. Дата устройства не используется для выбора на сервере;
относительное время в карточках остаётся относительно настоящего серверного
«сейчас». `due_today` в режиме tomorrow подписывается «Срок завтра».
Неизвестный срок не считается завтрашним. Правила архива и хранения не меняются.
# Состояние пар выбранного дня (0.4.2)

`day_lessons_state=finished` показывает «На сегодня пары закончились», `empty` —
«Сегодня пар нет» / «Завтра пар нет». При `unknown` нельзя утверждать, что день
пуст или закончился. `next_lesson` отображается только при дате начала в выбранном
календарном дне группы: будущая пара не подменяет завершённый сегодняшний день.
# Предмет в контексте пары (контракт 0.5.0)

Карточка ближайшей/текущей пары открывает `/subjects/lessons/:lessonId`, а не
расписание. `GET /lessons/{lesson_id}/subject` возвращает выбранную пару и её дату,
связанные ДЗ и состояние подключения событий/материалов. Клиент не сопоставляет
предметы по заголовкам и не выводит тип КТ из названия ДЗ. Названия из расписания
с многоточием не восстанавливаются догадкой. Возврат из страницы сохраняет выбор
«Сегодня / Завтра». Личные отметки и конфликт ревизии обновляют кеш страницы предмета.
События/КТ и материалы остаются явно `not_connected`; это не пустые данные и не моки.
Общий список `/subjects` пока остаётся подготовленным разделом.
# Важные дедлайны (контракт 0.6.0)

`/deadlines` получает `GET /deadlines` без моков в локальном real-preview. КТ,
контрольные и тесты не являются Homework и не имеют личной отметки выполнения ДЗ.
«Сегодня» показывает первые три актуальные записи и ссылку на весь список;
архив доступен через `?archive=true`. У записей точная дата, период и приблизительная
формулировка не смешиваются. Страница предмета теперь рендерит реальные `events`
при `events_state=ready`. Материалы по-прежнему не подключены. Панели записи
раскрываются штатным `<details>`; иконка КТ берётся из уже переданных ассетов Claude.
