# StudGroup — Design handoff: аудит макетов и ассетов (Stage 0)

## Карточка и детали события — 2026-10-06

Во всех списках событий заголовок карточки — предмет, ниже краткая задача и
дата либо период. Полный текст и контекст уточнения не раздувают карточку.
Нажатие открывает `/deadlines/:deadlineId`: предмет, тип события, задача, срок
и полные требования. Возврат сохраняет исходный экран и его фильтр. Период с
exclusive window_end=16 октября отображается до 15 октября включительно.
Контрольная точка не получает кнопку личного выполнения домашнего задания.

## Переключатель «Задания / Дедлайны» — 2026-10-06

Общий заголовок двух экранов: активный раздел крупнее и ярче, неактивный
меньше и бледнее, как «Сегодня / Завтра». Кнопки находятся в общей оболочке
и не пересоздаются при смене раздела, поэтому анимация размера и цвета не
обрывается. Фильтры каждого раздела остаются под заголовком. Отдельная кнопка
«Назад» у списка дедлайнов больше не нужна: это соседний раздел «Заданий».

## Главная: только ближайшие дедлайны — 2026-10-06

На «Сегодня» превью дедлайнов показывает максимум три события на ближайшие
7 дней относительно серверного времени, включая уже начавшиеся незавершённые
периоды сдачи. Неопределённые даты и дальние события остаются в полном разделе
«Дедлайны». Просроченные события исключаются; даты без времени действуют до конца
дня группы. Если подходящих событий нет, весь блок вместе с заголовком скрывается.

## Решение владельца — 2026-10-06: предупреждение об уточнении

В списках ДЗ и деталях студент видит «Требует уточнения» только когда срок
неизвестен даже после попытки расчёта по следующей паре. Староста (`membership.role = headman`)
видит предупреждение и при известной, но неподтверждённой дате. Дата по расписанию
не становится подтверждённой: исходные `status` и `verification_state` сохраняются.
Отмена, значимое изменение после выполнения и сбой обработки не скрываются.
Локальный просмотр реального импорта по умолчанию показывает роль студента.

Следствия для реализации:
1. **Веса 750 и 650 — не стандартные.** Нужен **вариативный Inter** (`@fontsource-variable/inter`, ось `wght`, подмножества `cyrillic` + `latin`), а не статические 400/600/700; заменяет `@fontsource/inter` из §2. ### 6.4 Проверка контраста утверждённой палитры (расчёт WCAG по HEX, не по макетам)

| Пара | Light | Dark | Вердикт |
| --- | ---: | ---: | --- |
| primary text / background · surface · elevated | 17.8 · 18.9 · 18.4 | 17.7 · 16.9 · 15.5 | ✅ |
| secondary text / surface | 4.52 | 8.72 | ✅ (на тонком пределе) |
| secondary text / background | **4.26** | 9.18 | ⚠ light < 4.5 |
| secondary text / elevated | **4.41** | 8.03 | ⚠ light < 4.5 |
| белый текст / primary action | 5.32 | **4.11** | ⚠ dark < 4.5 (Button 14/650 не «крупный») |
| primary action как текст/ссылка / surface | 5.32 | **4.33** (4.56 на bg) | ⚠ dark на surface |
| белый текст / градиент (концы) | 4.35 · 5.03 | 4.23 · 4.18 | ⚠ в середине и dark < 4.5 |
| success как **текст** / surface | **2.62** | 9.30 | ❌ light |
| warning как **текст** / surface | **2.35** | 9.66 | ❌ light |
| danger как **текст** / surface | **3.76** | 5.85 | ❌ light |
| info как **текст** / surface | **3.24** | 7.69 | ❌ light |
| focus / surface · background (нужно ≥ 3 : 1) | 4.23 · 3.99 | 6.53 · 6.88 | ✅ |
| border / surface | 1.24 | 1.59 | декоративный; **не** граница интерактивного поля (3 : 1) |
| disabled / surface | 1.83 | 2.86 | допустимо для отключённых |

**Выводы и требования к дизайнеру (предложение, не решение):**
1. Семантические цвета success/warning/danger/info в light **нельзя** использовать как цвет мелкого текста; только как заливка/значок/полоса. Для текста статусов нужны отдельные токены `--sg-color-{success,warning,danger,info}-text` (напр. при ориентире ≥ 4.5 : 1 на белом: success ≈ `#0C804A`, warning ≈ `#AC6406`, danger ≈ `#C0362C`, info ≈ `#2473C8`; значения — на утверждение дизайнера). В dark сами цвета проходят.
2. Light secondary text `#68769A` на `background`/`elevated` ниже 4.5 : 1 для Meta 12/500: либо затемнить токен, либо использовать только на `surface`, либо увеличить размер/вес.
3. Dark primary action: белый текст на кнопке 4.11 : 1 — нужен более тёмный dark-вариант заливки кнопки или тёмный текст; то же для белого текста на dark-градиенте.
4. Бордер не может быть единственным признаком границы интерактивного элемента: рамка поля/чипа — отдельный токен ≥ 3 : 1 либо иной признак.
5. Красный цвет — только от поля `urgency` (Q23).

Пока дизайнер не ответит, в реализации используются утверждённые значения; для пунктов 1–3 заводятся токены-заглушки с пометкой `TODO(design)` и тестом контраста, который падает на значения < 4.5 : 1 для текста.

## 11. Карточка в списке «Сегодня» (ревизия 11)

Всегда: название, предмет, срок. Не более одной основной метки + опциональное «Срочно». Чипа «ДЗ» нет; источник, импорт, подтверждение и обработка — только в деталях. Фон всех карточек одинаковый; выполнение — иконка и метка.

Приоритет основной метки (`features/today/cardStatus.ts`):
1. «Отменено» (`status = cancelled`);
2. «Обновлено — проверьте»: задание выполнено, и `significant_updated_at` позже `my_state.completed_at` (`revision` — техническая версия карточки и не используется; отметка не сбрасывается);
3. «Требует уточнения»: `status` или `verification_state = needs_clarification` — всегда, в том числе при неизвестном сроке (временное безопасное правило до `uncertain_fields`);
4. «Выполнено мной».
«Срочно» — только по `urgency`, не показывается у отменённых. Срок неизвестен → строка даты «Срок уточняется»; при `needs_clarification` основная метка «Требует уточнения» сохраняется.

### 11.1 Требования к контракту (для Codex)
1. Нужен `uncertain_fields` (какие именно данные неопределены). До его появления «Требует уточнения» показывается при любом `needs_clarification`, даже если строка даты уже говорит «Срок уточняется»; после появления можно не дублировать, когда неопределён только срок.
2. «Обновлено — проверьте» опирается на `significant_updated_at` и `my_state.completed_at`; обе даты должны оставаться в ответах списка и деталей.

## 13. Экран «Задания» (контракт 0.4.0)

**Статус.** Экран подключён к сгенерированному `listHomework` / `HomeworkListResponse` и включён в production. **Работа с реальным backend не проверена**: проверено только на моках, контрактных примерах и в тестах; сквозная проверка — после запуска backend и PostgreSQL.

**Оформление** не менялось: те же `HomeworkCard`, одинаковый фон, смысловые иконки, одна статусная метка по приоритету, «Срочно» только из `urgency`; капсулы фильтров без счётчиков. Фильтр хранится в URL (`?filter=today|week|mine|archive`).

**Фильтры — серверные.** `filter=all|today|week|mine|archive`, `limit=50`. «Все» — актуальные задания, включая выполненные; «Сегодня»/«На неделе» — актуальные невыполненные со сроком в соответствующем календарном диапазоне группы; «Выполнено мной» — актуальные выполненные. «Архив» — отменённые и с прошедшим сроком, независимо от личной отметки. На клиенте только защита от наступившего срока по живым серверным часам; серверные фильтры повторно не считаются.

**Группировка (один раз, на клиенте)** — порядок утверждён владельцем: «Ближайшие» (включая срок сегодня), «Срок уточняется», «Выполнено», «Просрочено», «Отменено». Пустые секции и их заголовки не выводятся. Внутри секции — сортировка для показа (ближайший срок первым; просроченные — недавние первыми; выполненные — новые отметки первыми). Порядок сервера (`created_at`, `id`) нужен только для курсора.

**Пагинация.** `useInfiniteQuery`, страницы по 50, кнопка «Загрузить ещё». Страницы объединяются по `id` (позиция — по первому появлению, данные — самые свежие). Пустая страница при непустом `next_cursor` не означает пустой список — клиент догружает дальше. Живые часы — `generated_at` последней страницы, не часы устройства (`server_time` заморожен на цепочку курсоров).

**Сброс курсоров.** Смена фильтра; отметка выполнения и её отмена (успех и конфликт ревизии) — список сбрасывается и загружается с первой страницы, Today и детали обновляются как раньше; возврат на экран спустя > 30 с или после скрытия приложения — перезапуск, чтобы не использовать устаревшие курсоры (15 минут). `422 invalid_request` при «Загрузить ещё» — один автоматический перезапуск списка, без цикла; если не помогло — ошибка.

**Состояния.** Загрузка (скелетоны), ошибка с повтором, нет доступа (403), офлайн, пустой результат для каждого фильтра, ошибка догрузки: уже загруженные карточки остаются, показывается строка «Не удалось загрузить следующие задания» с «Повторить».

**Архив.** Отменённые уходят туда сразу; задания с точным временем — при наступлении срока, с датой без времени — на следующий календарный день группы. В Today архивных нет. Данные и личные отметки сохраняются до обычного срока хранения. Это заменяет прежние окна +12/+24 часа. По решению владельца архивные карточки нейтральные: серые иконки и текст, без плашек срочности, отмены, уточнения и обновления. Личное выполнение обозначает только небольшая доступная галочка. Статусы сохраняются в деталях; существующие заголовки секций не меняются.

**Моки (только dev/test).** `src/mocks/homeworkList.ts` реализует правила `GET /homework`: фильтры, порядок `created_at`/`id`, непрозрачные курсоры на 15 минут, привязанные к фильтру, заморозка времени выборки, 422 на чужой/просроченный курсор. Сценарии: `tasks-many` (128 карточек, 3 страницы), `tasks-empty`, `tasks-error`, `tasks-cursor-expired`, `tasks-more-fails`, `tasks-dup-page`, `tasks-empty-first-page`. В production-сборку они не попадают (`check-dist`).

### 13.1 Для Codex: что проверить на реальном backend

**Обновление владельца:** на экране «Сегодня» личное выполнение не скрывает задание с известным актуальным сроком: карточка остаётся в обычной секции с отметкой выполнения. После наступления срока работает архив. Выполненные без известного срока остаются скрыты. Это не меняет серверные фильтры списка «Задания».

1. Все пять фильтров, переход в архив на границе точного срока / полуночи группы; `week` — пн–вс по `group_timezone`.
2. Курсор: `422 invalid_request` на просроченный (15 мин) и чужой курсор/фильтр; стабильная пагинация без дублей при изменениях между страницами (клиент всё равно объединяет по `id`).
3. Отменённые доступны только в архиве независимо от `cancelled_at`; данные не удалены. Статус отмены виден в деталях, не плашкой на архивной карточке.
4. `freshness` / `processing` в списке — клиент сейчас их не показывает; сообщите, нужны ли баннеры как в Today.
5. Поведение `mine` для отменённых и `my_state.completed_at` / `significant_updated_at` (нужны для «Обновлено — проверьте»).

# Страница предмета по нажатию на пару

Рабочий маршрут `/subjects/lessons/:lessonId`: название предмета, календарная дата
выбранной пары, её время/место/преподаватель при наличии, реальные связанные ДЗ.

макет этой страницы; контракт и поведение уже зафиксированы в 0.5.0.
